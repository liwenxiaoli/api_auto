## 一、项目条目（可直接粘贴进简历）

### 版本 A：合在接口自动化项目里（推荐，简历更紧凑）

**接口自动化测试框架 | Python + pytest + requests**

- 搭建数据驱动接口自动化框架：YAML 用例、占位符变量池、多环境切换（dev / test / mock）、
  JSON Schema 结构契约校验、数据库结果校验，共 **35 条用例**，接入 GitHub Actions
  冒烟 + 定时回归双层 CI。
- 自建 **Flask + waitress + SQLite mock 服务**作为白盒被测对象，同时提供 HTTP 接口与
  直连数据库两条校验通道，解决第三方接口不可控、无法查库的问题。
- 使用 **Locust** 对 mock 服务做性能测试与调优：400 并发下吞吐 **1289 → 2491 RPS（+93%）**，
  P50 延迟 **140ms → 5ms**，错误率 0%。

### 版本 B：单独作为性能测试项目（简历空间够时用这个）

**接口性能测试与瓶颈定位 | Locust + waitress + SQLite**

- 对自建 Flask 接口服务做压测，逐步定位并解决 5 处瓶颈，400 并发下吞吐
  **1289 → 2491 RPS（×1.93）**，P50 **140ms → 5ms**，错误率 0%。
- 通过「响应时间分位数是否同步上涨」区分「请求进不来」与「服务端处理不过来」两类瓶颈，
  先后定位 `connection_limit` 默认值 100、GIL 线程模型、每请求新建数据库连接三处问题。
- 用微基准（microbenchmark）拆分单请求成本：建连接 0.307ms、查询 0.291ms，
  占单请求 CPU 时间的 77%，据此改为线程本地连接复用，去掉每请求建连。
- 优化后先跑接口回归（3 条数据库校验用例全绿）再复压，确保性能改动未破坏功能。
- 发现同一配置两次测量相差 25%，先修测量方法（缩短爬坡、串行执行、三次取中位数），
  把方差压到 3% 以下；再用「两组数据区间是否重叠」而不是百分比大小判定优化是否生效。
- 因写入与读取共用同一 SQLite 文件，将日志模式切换为 WAL（读不加文件锁），
  实测吞吐 2281 → 2376 RPS（+4.1%）、P50 13ms → 8ms。
- 明确测量边界：本机单客户端约 2500 RPS 即报 CPU 过载，横向扩展结论不外推，
  需分布式压测才能验证。

### 数字的边界（面试前必读）

| 数字 | 状态 |
|---|---|
| 1289 → 2491（×1.93） | ✅ 同一测量方法、前后脚对比，站得住 |
| 2491 是服务端上限 | ❌ 不能说。压测端已报 `CPU too high`，只能说"≥2491" |
| 2281 / 2376 | ✅ 严格 A/B（各 3 次，区间不重叠），WAL 那组 |
| 绝对值到底多少 | 随测量参数在 **2280~2490** 之间漂，对外说"约 2.3k RPS，是优化前 1.8 倍以上" |

被追问"为什么两次测出来不一样"时，答：**爬坡占比、客户端 CPU、是否并发跑**——这三个都会动数字，
所以我们的对比一律固定协议、跑三次取中位数。

## 二、项目描述（面试口述 60 秒版）

> 我做了一个接口自动化项目，被测对象是我自己用 Flask + waitress + SQLite 搭的 mock 服务，
> 这样既能调接口又能直接查库。
>
> 性能这块我用 Locust 压，一开始只有 1289 RPS，P50 还有 140 毫秒。
> 我把压测数据拆开看：加线程没用、加进程也没用、加用户反而更慢，说明问题不在并发度，
> 而在每个请求自己的开销上。于是写了个微基准单独给数据库那段计时，
> 发现「每请求新建一条 SQLite 连接」就占了 40% 的时间。
> 改成每个线程复用自己的连接之后，吞吐到 2491，P50 掉到 5 毫秒。

## 三、三条可直接背的亮点句

1. 「**同一句“RPS 卡住”，Med 不涨和 Med 涨是两个相反的原因**：不涨说明请求没进来，
   要查压测机和连接数上限；涨了才是服务端在排队。」
2. 「**加线程和加进程都没用的时候，问题一定在单个请求内部**，这时候该做微基准，
   而不是继续加压。」
3. 「**性能优化前先跑功能回归**，否则你可能优化了一个坏掉的服务。」

## 四、面试追问预案

| 会被问什么 | 怎么答（要点） |
|---|---|
| 怎么确定瓶颈在数据库，不是 Python 代码？ | 微基准拆分：单独给「建连接」和「查询」各跑 1000 次，得 0.307ms / 0.291ms；再和压测反推的单请求 CPU 0.78ms 对比，数据库占 77% |
| 为什么加线程没用？ | GIL 每进程一把，8 个线程仍只占 1 个核；实测 4→8 吞吐反降 12%，多出来的是抢锁和上下文切换开销 |
| 为什么加进程也没用？ | 800 用户双进程 1217 RPS，单进程 1249，加进程零收益 —— 说明瓶颈是每个请求自身开销，与并发度无关 |
| 2491 是服务端上限吗？ | 不是。Locust 已报 `CPU usage was too high`，压测端先到顶，所以真实上限 ≥ 2491，要继续测得上分布式 |
| 怎么保证优化没改坏功能？ | 改完先 `pytest --env=mock` 跑 3 条数据库校验用例，全绿再压测 |
| 踩过什么坑？ | Windows `select()` 512 句柄上限（800 并发直接崩）、Flask 自带 dev server 单线程、waitress `connection_limit` 默认 100 造成「Med 不涨但 Max 45 秒」 |
| 为什么用 P95 不用平均值？ | 平均值会被少数慢请求掩盖，反向也会被少量极值拉高；P95/P99 看的是大多数用户的真实体验 |
