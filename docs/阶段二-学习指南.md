### 读代码的顺序

**① `common/client.py`（最重要的一个文件）**

整个文件就干一件事：**所有请求从一个口子出去**。

```python
resp = self.session.request(method, url, timeout=self.timeout, **kwargs)
```

三个关键点：
- `base_url` 自动拼 —— 用例里只写 `/products`，换环境改 yaml 就够
- `timeout` 强制传 —— **不设超时，接口挂了你的用例会永远卡住**，这是新手最常犯的错
- `requests.Session()` —— 自动保持 Cookie、复用 TCP 连接

对比一下你以前写的 `request_util.py`，看看少了什么（多半是超时和 Session）。

**② `conftest.py`（接口关联的枢纽）**

```python
@pytest.fixture(scope="session")
def token(client):
    resp = client.post("/auth/login", json={...})
    return resp.json()["access_token"]
```

`scope="session"` 的意思：**整个测试过程只登录一次**，所有用例共用这个 token。
如果每条用例都登录一遍，慢不说，还容易被服务端限流。

用例里怎么用它？看 `test_profile_with_token(self, auth_client)` ——
参数名写 `auth_client`，pytest 就自动把"带 token 的客户端"送进来。**这就是接口关联。**

**③ `common/json_util.py`（jsonpath）**

```python
json_get(resp.json(), "category.name")     # 取嵌套字段
json_get(resp.json(), "[0].title")         # 取列表第一条
```

好处：取不到返回 `None` 而不是崩溃。而且路径能写进 yaml，是后面做"通用断言"的基础。

## 第 6 周：通用 extract 机制（接口关联的配置化）

### 要解决的问题

第 4-5 周的写法是这样（写在 Python 里）：

```python
token = resp.json()["access_token"]
client.get("/auth/profile", headers={"Authorization": f"Bearer {token}"})
```

能用，但有两个毛病：
1. **token 只活在这一个函数里**，换个用例就得再写一遍
2. **用例数据搬到 yaml 之后，就没地方写这行 Python 了**

所以要把它拆成"配置 + 通用代码"两半：

| 名词 | 作用 | 文件 |
|---|---|---|
| 变量池 Context | 公共存钱罐，谁都能存、谁都能取 | `common/context.py` |
| extract 规则 | 从响应里取值存进池子（存钱） | `common/extractor.py` |
| `${token}` 占位符 | 发送前自动替换成真实值（取钱） | `common/context.py` 的 `render()` |
| 用例执行器 | 把 5 步流程固化，用例只留数据 | `common/runner.py` |

### 数据长什么样（`data/extract_cases.yaml`）

```yaml
- case: 登录成功并把 token 存进变量池
  request: {method: POST, path: /auth/login, json: {email: john@mail.com, password: changeme}}
  expect_status: 201
  extract:
    token: $.access_token          # 左边是起的名字，右边是 jsonpath 表达式

- case: 用变量池里的 token 访问个人信息
  request:
    method: GET
    path: /auth/profile
    headers: {Authorization: "Bearer ${token}"}    # 发送前自动换成真实 token
  expect_status: 200
  expect:
    $.email: john@mail.com
```

5 条用例的顺序闭环：登录取 token → 带 `${token}` 查资料 → 建商品取 `${product_id}` → 查详情 → 删除清理。

### 执行一次用例的 5 步（`common/runner.py`）

```
渲染占位符 → 发请求 → 断言状态码 → extract 提取变量 → 断言 expect 字段
```

因为流程固化了，`testcases/test_extract.py` 里**几乎没有代码**，
只有 parametrize + 一行 `run_case(client, case, ctx)`。**加场景 = 改 yaml，代码不动。**

### 三个必须记住的设计点

1. **`ctx` 必须是 session 级**：变量池的价值就是"上一条存、下一条取"，
   每条用例新建空池子就谁也取不到别人的值。
2. **headers 走 `kwargs` 是一次性的**，只对本次请求生效，不会污染后面的用例
   （对比第 2 课把 `remove_header` 注释掉导致 `200 != 401` 的实验）。
3. **extract 取不到必须报错**，不能静默跳过 —— 否则后面用例会以莫名其妙的方式失败。

### 热加载函数：让数据每次都不一样

有些数据写死就跑不过第二次（手机号、订单号、标题会被判"已存在"）。
解决：yaml 里写**函数调用**，执行到那一刻才现算。

```yaml
title: "auto-${random_str(8)}"     # 每次跑生成一个新后缀
phone: "${gen_phone()}"
order_no: "${timestamp()}"
```

可用的函数都在 `common/functions.py`：`gen_phone()` / `timestamp()` / `timestamp_ms()` / `random_str(n)` / `uuid_hex()`。

原理三步（见 `common/context.py:: _lookup`）：
1. 正则发现占位符里带括号 → 判定为函数调用
2. `getattr(functions, 名字)` 去 `functions.py` 里找这个函数
3. 找到就调用，找不到就报"可用的有：xxx"

> 安全：只能调 `functions.py` 里定义的函数。yaml 里写 `${os.system(...)}` 不会被执行。

实测日志（连跑两次，值都不同）：
```
热加载 random_str(8) -> gq7opmib
热加载 random_str(8) -> c9r14f95
```

### 清理保障：中间失败也不留垃圾

**问题**：yaml 用例是顺序依赖的（创建 → 查询 → 删除）。
如果中间某条失败导致后面的"删除"没跑到，商品就残留在测试站上，越积越多。

**做法**：给用例加 `cleanup` 字段，框架登记下来，全部跑完后统一清理。

```yaml
  cleanup:
    method: DELETE
    path: /products/${product_id}
    headers: {Authorization: "Bearer ${token}"}
```

两个细节：
1. `runner.py` 把登记清理放在 **expect 断言之前** —— 这样即使断言失败抛异常，数据也已被记下
2. `conftest.py` 里用 `autouse=True` 的 session fixture 做收尾（不用在用例里写名字）

实测日志：
```
清理测试数据 DELETE /products/545 -> 200
清理测试数据 DELETE /products/546 -> 200
```

## 第 8 周：请求签名 + CI 自动跑

### 签名是什么、为什么需要

客户端和服务端事先约定一个**密钥**（secret，只有两边知道）。发请求前按规则把参数
拼成串、加上密钥算 md5，把结果一起发给服务端；服务端用同样规则算一遍，对得上才放行。

作用：**防篡改**（改参数签名就对不上）+ **防乱调**（不知道密钥算不出 sign）。

常见规则（各公司略有差异，这里是通用版）：

1. 去掉 `sign` 本身和空值
2. 按参数名排序（保证字典顺序不同也能算出一样的值）
3. 拼成 `k1=v1&k2=v2`
4. 尾部拼密钥：`k1=v1&k2=v2&key=SECRET`
5. 算 md5，转 32 位小写

代码在 `common/sign.py`，**不依赖网络**，所以可以单独写单元测试。

### 为什么给工具函数单独写测试（7 条，见 testcases/test_sign.py）

签名算错 → 接口全量 401 → 几十条用例一起红，**根本看不出是签名的问题**。
把签名逻辑单独测明白，接口用例失败时就只怀疑"参数/环境"，排查范围小一大半。

测的 7 个点：结果固定、参数顺序无关、空值和 sign 字段跳过、中文能签、
密钥为空必须报错、`add_sign` 不改原字典、原始串拼接规则。

### yaml 里怎么用（框架已集成，见 runner.py 的 `_apply_sign`）

```yaml
- case: 带签名查询商品列表
  request:
    method: GET
    path: /products
    params: {limit: 2}
  sign:
    secret: my_secret     # 真实项目应从配置/环境变量读
    on: params            # 对谁签名
    in: params            # 签名值放哪（也可放 headers）
  expect_status: 200
```

实测日志：

```
签名原始串: limit=2&key=my_secret
签名结果 sign = aa62e28daa4bd9eb1c4222eb7629521d
```

> 想再防"重放"（别人原样重发请求），在参数里加时间戳：`params: {timestamp: "${timestamp()}"}`。

### CI：让 GitHub 帮你定时跑

`.github/workflows/api-test.yml` 三种触发：推代码到 main、提 PR、**每天定时**（cron 用 UTC，
`'0 2 * * *'` = 北京时间 10:00），也可以在网页上手动 Run workflow。

关键点：`上传报告` 那一步写了 `if: always()` —— **失败也要上传**，否则看不到是哪条挂的。

README 顶部的徽章会自动显示运行状态（绿=通过，红=失败）。

### 改造分四步

| 步骤 | 做什么 | 文件 |
|---|---|---|
| 1 | yaml 统一成 `request / expect_status / extract / expect / cleanup` 结构 | `data/*.yaml` |
| 2 | 断言能力扩展（原来只有"相等"，不够用） | 新增 `common/asserter.py` |
| 3 | Python 只留 `parametrize + run_case` | `testcases/*.py` |
| 4 | token 由 fixture 自动塞进变量池，yaml 直接写 `${token}` | `conftest.py::init_context` |

### 断言的三种写法

```yaml
expect:
  $.email: john@mail.com       # ① 相等（原来的写法）
  $.price: {gt: 0}             # ② 高级：contains / not_empty / gt / lt
  "@length": 1                 # ③ 对整份响应断言（@ 必须加引号）
```

`expect_status` 也支持写列表：`[400, 404]` —— 同一个错误不同系统返回不一样，别写死。

> ⚠️ 实测踩坑：jsonpath 库对单独的 `$` 返回 **False**（不是整个响应），
> 所以"断言返回几条"不能用 `$.length`，得用 `@length` 这种对整体的断言。

### 一个重要取舍：顺序依赖

`product_cases.yaml` 里"取 id → 查详情""创建 → 查询"是**顺序依赖**的。
这是 extract 机制的代价：**用 `-k` 单独挑后面那条跑会失败**（拿不到变量）。

可以接受，因为：
- 整文件跑完全没问题
- 换来的是"不写死任何环境数据"（公共站数据随时被别人删）

### 结果

```

```

清理日志证明数据没残留：`清理测试数据 DELETE /products/165 -> 200`

| runner 六步 | ①渲染占位符 ②发请求 ③断言状态码 ④extract ⑤断言响应字段 ⑥断言数据库（可选） | `common/runner.py:45` `run_case` |

**⑥ 为什么可选**：只有 `mock` 环境配了 `db_path`（`config/config.yaml:29`）。dev/test 是公网，
连不到对方的数据库，写 `db_assert` 必然失败。所以数据库断言只写在 `data/db_cases.yaml`，
且那 3 条都打了 `mock` 标记，跑的时候必须 `-m mock --env=mock`。

**runner 六步里，只有 request 段发给服务器**：`expect_status` / `extract` / `expect` / `db_assert`
都留在本地，由 `run_case` 各步按需去取 `case` 字典里自己那一段。

### 层 2 第 1 节：变量池是什么（已结课 ✅）

**一句话：变量池就是 `ctx.data`，一个普通字典。** 没有数据库、没有文件、没有魔法。

```
ctx.data == {"token": "eyJhbGci...", "product_id": 162}
        键 = yaml 里 ${} 中间写的名字    值 = 真实数据（类型原样保留）
```

`common/context.py:35` 的 `self.data = {}` 就是它的全部定义。
`class Context` 是设计图，`Context()`（`conftest.py:55`）是盖出来的那套房，
`scope="session"` 保证**整轮测试只盖一套**，所有用例共用同一间储物间。

#### 写入：全项目只有两个调用点

| 谁调用 | 位置 | 塞什么 | 依赖用例跑过吗 |
|---|---|---|---|
| `init_context` | `conftest.py:66` `ctx.set("token", token)` | token | ❌ 会话开始就塞 |
| `extract()` | `extractor.py:37` `ctx.set(name, value)` | yaml 里 `extract:` 定义的变量 | ✅ 依赖那条用例执行到第 ④ 步 |

> ⚠️ `common/context.py:38` 的 `def set` 是**笔的定义**，不是调用点。别把定义当来源。

#### 关键时序：token 为什么"一开始就在"

```
① ctx                      → Context()                 池子此时是 {}
② client(ctx)              → HttpClient + attach_context(ctx)
③ token(client)            → POST /auth/login          拿到 access_token
④ init_context(ctx, token) → ctx.set("token", token)   ← autouse=True 自动执行
⑤ 你的用例函数体开始执行                                这时 ${token} 已经能取到值
```

这 5 步全部发生在**第一条被选中用例的函数体之前**，由 pytest 按参数依赖自动排队、懒加载。

#### 三个必须记住的结论

1. **token 的源头是 fixture，不是 extract。**
   `data/extract_cases.yaml:20` 那条 `extract: token: $.access_token` 只是**教学演示**，
   它是在重复覆盖一个早已存在的键。删掉它，其他用例的 `Bearer ${token}` 照样能跑。
2. **`${}` 取不到值会抛 KeyError，并把池子里的键全列出来**：
   `占位符 ${product_id} 没有值。变量池里现在只有：['token']`
   —— 这句报错就是最好的排错入口，先看"现在有什么"，再想"谁该塞它"。
3. **任何"筛掉部分用例"的手段都会切断依赖链**：`-m`、`-k`、xdist 默认 `--dist load`、`--lf`。
   上游造数据的用例没跑，下游必然缺料（10-31 的 `-n 4`、11-02 的 `-m smoke` 都是这个病）。

#### 两个动手实验（已验证）

```python
# testcases/test_pool.py —— 临时文件，跑完必须删（否则基线会从 34 变 37）
from config.settings import settings


def test_01(ctx):
    print("池子：", ctx.data)
    # 预期 {'token': 'eyJ...'} —— 证明 token 在用例执行前就已经在池子里了


def test_02(ctx):
    print(ctx.render("我是 ${name}"))
    # 预期 KeyError；且连"我是 "都不会打印
    # 原因：Python 先把参数算完才调用函数，render 在算参数时就抛了，print 根本没被调用
```

跑法：`pytest testcases/test_pool.py -s -q -k "01"`（`-s` 才能看到 print）。

**破坏实验**：把 `conftest.py:58` 的 `autouse=True` 删掉 → 没人请求 `init_context` → 池子变 `{}`
→ 全项目凡是 `${token}` 的用例全炸。改回来即可复原。

### 层 2 第 2 节：`${}` 是怎么被换成真值的（已结课 ✅）

**唯一入口是 `common/context.py:46` 的 `render()`**，全项目没有第二套替换逻辑：

| 传入类型 | 做什么 |
|---|---|
| `str` | 调 `_render_str` 替换里面的 `${}` |
| `dict` | 每个 **value** 递归替换，**key 一个字都不动** |
| `list` | 每一项递归替换 |
| 其它（int / bool / None） | **原样返回** → 所以 `expect_status: 201` 绝不会被碰 |

**正则** `context.py:25`：

```python
PLACEHOLDER = re.compile(r"\$\{([^}]+)\}")
#   \$ 字面量 $   \{ 字面量 {   ([^}]+) 捕获组=变量名   \} 字面量 }
#   [^}] 而不是 . ：遇到右括号就停，不会一路吃到底
```

**两条分支（本节核心）**：

| 场景 | 走哪条 | 结果 |
|---|---|---|
| `"${pid}"` 整串只有一个占位符 | `fullmatch`（`context.py:67`） | **原样返回，保留类型** → `123`（int） |
| `"Bearer ${token}"` 占位符只是一段 | `sub` + `str()`（`context.py:76`） | **结果必是字符串** |

为什么要区分：`{"price": "${price}"}` 若一律转字符串，服务器收到 `"199"` 而非 `199` → 422。
口诀：**整串只有一个占位符 → 保留类型；掺了别的字 → 全变字符串。**

**热加载 `${random_str(8)}`**：`_lookup` 发现名字带括号 → `FUNC_CALL` 拆出函数名和参数 →
`getattr(functions, name)` 去 `common/functions.py` 找函数 → 现算 → **结果直接返回，不进池子**。

| | 普通变量 `${token}` | 热加载 `${random_str(8)}` |
|---|---|---|
| 值从哪来 | 池子里取 | 当场调函数算出来 |
| 进池子吗 | 本来就是从池子拿 | 不进去 |
| 每次一样吗 | 一样 | 每次不同（所以注册不会撞"已存在"） |

安全设计：只能调 `common/functions.py` 里定义的函数，yaml 里写别的函数只会报"不存在"，不会被执行。

**render 的调用点全景**：`runner.py:74/76/79`（params / json / headers）、`runner.py:99`（cleanup）、
`client.py:27`（**path**，绕开 runner 直接调 client 时也要能渲染）、`client.py:30`（兜底再渲染一次，幂等）、
`asserter.py:45`（expect 的期望值）、`asserter.py:71/72`（db_assert 的 sql 和期望值）。

### 层 2 第 3 节：extract —— 谁把值塞进池子（已结课 ✅）

位置：第 ④ 步，`runner.py:94` `extract(data, case.get("extract"), ctx)`。
它在 ③ 断言状态码**之后** —— 状态码都错了，响应里没东西可提。

`common/extractor.py:27-38` 一个循环干三件事：

```python
value = json_get(resp_json, expr)   # ① 按 jsonpath 从响应里取值
if value is None: raise AssertionError(...)  # ② 取不到立刻报错
ctx.set(name, value)                # ③ 存进池子（这就是第 1 节那两个写入口之一）
```

yaml 写法：`product_id: $.id` —— **左边自己起名字，右边 jsonpath 表达式**。项目里真实用法：

| 写法 | 意思 |
|---|---|
| `product_id: $.id` | 响应顶层的 id |
| `token: $.access_token` | 顶层字段 |
| `any_id: $[0].id` | 响应是列表时取第 0 条 |
| `category.name` | 嵌套取值（语法通用） |

`json_util.py:25`：`result[0] if len(result) == 1 else result` —— jsonpath 永远返回列表，
匹配到 1 个时脱掉列表外壳，否则存进池子会变成 `/products/[162]`。

**为什么取不到要炸而不是跳过**（`extractor.py:32`）：

- 跳过 → 上游用例还显示 PASSED，病根藏起来；下游才炸 `KeyError: 占位符 ${product_id} 没有值`，
  **报错点 ≠ 出错点**，中间可能隔十几条用例，还得回头翻
- 当场炸 → `提取失败：表达式 $.idd ... 实际响应是：{...}`，**报错点 = 出错点，还附赠响应全文**

口诀：**报错要发生在出错的地方，并且自己能说出原因。**
（已知粗糙点：字段真实值本来就是 `null` 时也会被判"提取失败"，目前项目没用到这种字段。）

**cleanup 为什么必须排在 ④ 之后**（`runner.py:94` vs `98`）：
`cleanup` 的 path 里写着 `${product_id}`，④ 没跑就没值，登记时直接 KeyError；
且登记放在 ⑤ 断言之前，这样即使断言失败，脏数据照样在结束时被删掉。

### 层 2 收尾：6 步串成一条线（已毕业 ✅）

**核心结论：6 步里只有 ①（读池子）和 ④（写池子）动池子，② ③ ⑤ ⑥ 一次都不碰。**

所以它解释了所有"取不到值"的故障：上游那条没跑成 → 没人执行第 ④ 步 → 下游第 ① 步必然 KeyError。
`-n 4`（拆到不同进程）和 `-m smoke`（上游被筛掉）报的是**同一个病**。

#### ⚠️ 最容易混的一点：两个 `$` 不是一回事

| 写法 | 出现在 | 作用对象 | 值从哪来 |
|---|---|---|---|
| `$.id` | `extract` 右边、`expect` **左边** | **响应体**（服务器返回的 JSON） | 服务器 |
| `${product_id}` | `request` 里、`expect` **右边** | **变量池** `ctx.data` | 上游用例第 ④ 步 / fixture |

**有花括号 `${}` = 占位符，去池子取；只有 `$` 加点号 `$.` = jsonpath，去响应里取。**

`$.id` 的值是**服务器给的**：POST 创建商品 → 服务器生成 id 并返回完整记录 →
`runner.py:91` `data = resp.json()` → ④ 用 `$.id` 从这份 data 里抠出 147。
**extract 是搬运工，不是生产者。**

由此得到"新用例能不能只用 `${product_id}`"的判断前提（三条同时成立才安全）：

1. 同一次运行里，**排在它前面的某条用例**执行过第 ④ 步
2. 上游**没被筛掉**（`-m` / `-k` / `--lf`）
3. 上游跟它**在同一进程**（xdist 必须 `--dist loadfile`，同文件才不分家）

> 这三条在层 3 被彻底取消：改成 fixture 提供公共数据 + 私有变量加文件前缀之后，
> 用例不再依赖"别人先跑过"。见下面「层 3 第 3 块」。

### 层 3 第 1 块：数据库校验（已结课 ✅）

**动机**：接口说"成功了"，数据库里未必真有。四种典型故障 ——

| 情况 | 接口返回 | 数据库实际 |
|---|---|---|
| 只写缓存 / 异步落库失败 | 201 | **没这条记录** |
| 字段被截断或类型转换 | 201 | `price` 存成了字符串 |
| 事务回滚了但接口照样返回成功 | 201 | **没这条记录** |
| 软删除 | 200 | 记录还在，只是打了删除标记 |

只校验响应 = 只听服务员说"菜做好了"；直连查库 = 自己进厨房看锅里有没有。

#### 位置：第 ⑥ 步，且是**唯一可选**的一步

`runner.py:104` 无条件调用 `assert_db(case.get("db_assert"), ctx)`，跳过逻辑在函数内部两道门：

```python
if not conf:                    # 门 1：这条用例没写 db_assert → 直接返回
    return
if settings.db_path is None:    # 门 2：这个环境没配 db_path → 打 warning 后返回
    return
```

- 门 1：34 条里 31 条没写 `db_assert`，走到这行就返回，零影响
- 门 2：**只有 mock 环境配了 `db_path`**（`config/config.yaml:29`）。dev/test 是公网
  escuelajs，连不上别人的库，写了必然失败

#### 五小步（`asserter.py:63-90`）

```yaml
db_assert:
  sql: SELECT name, price, stock FROM products WHERE id = ${product_id}
  expect: [小米15, 4999, 30]
```

① 渲染 SQL 里的 `${product_id}` → ② 渲染期望值 → ③ `query_one(sql)` 查一行 →
④ **先确认查得到**（查不到就报"一条都没查到"）→ ⑤ `list(row) == list(expected)` 逐列比对

两个坑：

- **按列顺序比对**：`SELECT name, price, stock` 对应 `[小米15, 4999, 30]`，顺序写反必红
- **`expect: null` 不是"不比对"**，是断言"**一条都查不到**"，用于删除类场景
  （软删除的反例：接口 200，库里记录还在）

#### 为什么只有 mock 能验（物理原因）

- dev/test 只有一条路：HTTP → 别人的服务器 → 别人的数据库（进不去）
- mock 有两条路：HTTP 进 Flask 写 SQLite；**测试进程直接 `sqlite3.connect` 打开
  `mock/shop.db`** —— 因为库文件就在你本机

#### `common/db.py` 四个必须记住的点

| 点 | 为什么 |
|---|---|
| `sqlite3.connect(settings.db_path, timeout=10)` | 路径只在配置写一次，不硬编码 |
| `finally: conn.close()` | 不关门文件被占住，别人的写会锁死；`finally` 保证出错也关 |
| `execute()` 自带 `commit()` | 不 commit 只存在连接里，一关就没（幽灵数据） |
| `timeout=10` | SQLite 同时只允许一个写；脚本在查、mock 在写，撞上要排队 |

**破坏实验（已验证）**：注释 `mock/app.py` 的 `conn.commit()` → 接口照样 201
（响应是 `jsonify` 手拼的），但第 ⑥ 步报"期望查得到记录，实际一条都没查到"。
这就是"接口撒谎"的现场复现：**响应谁拼的、落库谁干的，是两条独立的路**。

### 层 3 第 2 块：marker 用例分级（已结课 ✅）

| 标记 | 条数 | 含义 |
|---|---|---|
| `smoke` | 5 | 提代码前跑，核心正向链路 |
| `mock` | 3 | **只能在本地 mock 环境跑**，公网必挂 |
| `regression` | 0 | 已注册、暂未使用（`pytest.ini` 里的预留位） |

**关键差异：标记打在"数据"上，不是函数头上。** 一条 yaml 就是一条用例，
`test_product.py` 里只有一个函数扛所有数据，函数级标记会把整个文件都标成 smoke。
所以 `common/yaml_util.py` 里用：

```python
marks = [getattr(pytest.mark, m) for m in case.get("marks", [])]   # 字符串 → 标记对象
params.append(pytest.param(case, marks=marks, id=case.get("case")))
```

**`--strict-markers` 防"假绿"**：拼错标记名（`smok`）不加严格模式只 warning，
然后筛出 0 条、全绿通过 —— 你以为跑了冒烟，其实一条没跑。

**`-m` 和 `--env` 是两件事，必须一起给：**

| 写法 | 管什么 |
|---|---|
| `-m mock` | 跑**哪些**用例（按标记筛） |
| `--env=mock` | 发给**哪台**服务器（选配置） |

只写一个的两种翻车（实测）：

- 只写 `--env=mock` → **34 条全跑**（不是 0 条），mock 服务不认识大部分接口 → 大面积红
- 只写 `-m mock` → 环境回落到**默认 dev**（`base_url` 是公网），3 条用例全 500

> 默认环境从来不是"不确定"，是 `dev`。

**打 smoke 的铁律**：被选中的每一条都必须能**独立跑通**，不能有"必须排在某条后面"的隐形前提。

### 层 3 第 3 块：前置数据 fixture —— 根治顺序依赖（已落地 ✅）

#### 病症

用例 A 的第 ④ 步塞值、用例 B 的第 ① 步取值，靠"同文件 + 顺序执行"活着。四种场景立刻断链：
`-k` 单跑、`-m` 筛掉上游、xdist 默认 `load` 拆散、用例顺序变动。

#### 药方：把"造数据"从用例搬进 fixture

`conftest.py` 的 `existing_product(client, ctx, token)`：

```python
resp = client.post("/products/", headers={"Authorization": f"Bearer {token}"}, json={...})
assert resp.status_code == 201, f"前置数据没造出来：{resp.status_code} {resp.text}"
data = resp.json()
ctx.set("product_id", data["id"])
ctx.set("product_title", data["title"])
ctx.set("product_price", data["price"])
ctx.add_cleanup({...})          # 登记删除，session 结束时统一清理
return data["id"]
```

四个设计点：

| 设计 | 理由 |
|---|---|
| **不加 `autouse=True`** | 加了会让**所有**用例（含只能跑 mock 的 3 条 db 用例）都先建商品，而 mock 表结构是 `name/price/stock`、公网是 `title/description/categoryId`，必红。正确做法是在需要的测试函数**参数里写名字**，pytest 按名注入 |
| `f"Bearer {token}"` 而不是 `"Bearer ${token}"` | 值已在手边，直接拼；`${}` 留给"手边没有、要框架现算"的值（如 `"auto-fixture-${random_str(6)}"` 的标题） |
| `assert 201` | 前置数据没造出来就当场炸，不让下游以"占位符没值"的方式失败 |
| `ctx.add_cleanup` | 造完要负责删，否则公网数据越攒越多，分页/查询类断言会跟着变 |

> `scope="session"` 的 fixture 在**每个 worker 各执行一次** —— 这正是根治并发的关键：
> 不管用例被分到哪个进程，那个进程的池子里都有料。

#### 第二个病：跨文件键名污染（变量池是全局命名空间）

同一份池子里，`extract_cases.yaml` 和 `product_cases.yaml` 都往 `product_id` 写，
且两边造的数据不同（88 元 / 99 元）。并发时后写者覆盖先写者 → 偶发
`期望 99，实际 88`（串行不出现，所以极难复现）。

**修法：私有变量加文件前缀做命名空间隔离。**

| 文件 | 私有键 | 公共键（只由 fixture 写） |
|---|---|---|
| `extract_cases.yaml` | `extract_product_id / _title / _price` | `product_id / product_title / product_price` |
| `product_cases.yaml` | `created_product_id / _title` | 同上 |
| `db_cases.yaml` | `db_product_id` | —— |

**同时必须消灭"写死的期望值"**：`$.price: 99` 这种常量隐含"我查到的必须是上一条造的那个"。
改成 `$.price: ${product_price}`，让 **path 和 expect 同源** —— 查谁就用谁的标准，
换条用例造的数据也不会对不上。

> 代价要认：这样改完，那条用例实际查的是 fixture 造的商品，不再是"上一条刚创建的商品"，
> 用例名已改为「按 id 查询商品（id 和期望值都来自变量池）」。
> 真需要"创建后立刻查"的闭环，正确做法是把它做成**一条用例**或交给 fixture，而不是靠执行顺序。

## 三条硬规矩（和 UI 项目一样）

1. **必须设超时** —— `HttpClient` 已经帮你做了，不要绕过它直接用 `requests.get`
2. **自己造的数据自己清** —— 创建类用例一律用 `try/finally` 删除
3. **断言要断言业务字段** —— 只断言状态码 200 是不够的，那只能证明"接口没崩"，
