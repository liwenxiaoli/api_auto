### 读代码的顺序

**① `common/client.py`（最重要的一个文件）**

整个文件就干一件事：**所有请求从一个口子出去**。

```python
resp = self.session.request(method, url, timeout=self.timeout, **kwargs)
```

三个关键点：
- `base_url` 自动拼 —— 用例里只写 `/products`，换环境改 yaml 就够
- `timeout` 强制传 —— **不设超时，接口挂了你的用例会永远卡住**，这是新手最常犯的错
- `requests.Session()` —— 自动保持 Cookie、复用 TCP 连接

对比一下你以前写的 `request_util.py`，看看少了什么（多半是超时和 Session）。

**② `conftest.py`（接口关联的枢纽）**

```python
@pytest.fixture(scope="session")
def token(client):
    resp = client.post("/auth/login", json={...})
    return resp.json()["access_token"]
```

`scope="session"` 的意思：**整个测试过程只登录一次**，所有用例共用这个 token。
如果每条用例都登录一遍，慢不说，还容易被服务端限流。

用例里怎么用它？看 `test_profile_with_token(self, auth_client)` ——
参数名写 `auth_client`，pytest 就自动把"带 token 的客户端"送进来。**这就是接口关联。**

**③ `common/json_util.py`（jsonpath）**

```python
json_get(resp.json(), "category.name")     # 取嵌套字段
json_get(resp.json(), "[0].title")         # 取列表第一条
```

好处：取不到返回 `None` 而不是崩溃。而且路径能写进 yaml，是后面做"通用断言"的基础。

## 第 6 周：通用 extract 机制（接口关联的配置化）

### 要解决的问题

第 4-5 周的写法是这样（写在 Python 里）：

```python
token = resp.json()["access_token"]
client.get("/auth/profile", headers={"Authorization": f"Bearer {token}"})
```

能用，但有两个毛病：
1. **token 只活在这一个函数里**，换个用例就得再写一遍
2. **用例数据搬到 yaml 之后，就没地方写这行 Python 了**

所以要把它拆成"配置 + 通用代码"两半：

| 名词 | 作用 | 文件 |
|---|---|---|
| 变量池 Context | 公共存钱罐，谁都能存、谁都能取 | `common/context.py` |
| extract 规则 | 从响应里取值存进池子（存钱） | `common/extractor.py` |
| `${token}` 占位符 | 发送前自动替换成真实值（取钱） | `common/context.py` 的 `render()` |
| 用例执行器 | 把 5 步流程固化，用例只留数据 | `common/runner.py` |

### 数据长什么样（`data/extract_cases.yaml`）

```yaml
- case: 登录成功并把 token 存进变量池
  request: {method: POST, path: /auth/login, json: {email: john@mail.com, password: changeme}}
  expect_status: 201
  extract:
    token: $.access_token          # 左边是起的名字，右边是 jsonpath 表达式

- case: 用变量池里的 token 访问个人信息
  request:
    method: GET
    path: /auth/profile
    headers: {Authorization: "Bearer ${token}"}    # 发送前自动换成真实 token
  expect_status: 200
  expect:
    $.email: john@mail.com
```

5 条用例的顺序闭环：登录取 token → 带 `${token}` 查资料 → 建商品取 `${product_id}` → 查详情 → 删除清理。

### 执行一次用例的 5 步（`common/runner.py`）

```
渲染占位符 → 发请求 → 断言状态码 → extract 提取变量 → 断言 expect 字段
```

因为流程固化了，`testcases/test_extract.py` 里**几乎没有代码**，
只有 parametrize + 一行 `run_case(client, case, ctx)`。**加场景 = 改 yaml，代码不动。**

### 三个必须记住的设计点

1. **`ctx` 必须是 session 级**：变量池的价值就是"上一条存、下一条取"，
   每条用例新建空池子就谁也取不到别人的值。
2. **headers 走 `kwargs` 是一次性的**，只对本次请求生效，不会污染后面的用例
   （对比第 2 课把 `remove_header` 注释掉导致 `200 != 401` 的实验）。
3. **extract 取不到必须报错**，不能静默跳过 —— 否则后面用例会以莫名其妙的方式失败。

### 热加载函数：让数据每次都不一样

有些数据写死就跑不过第二次（手机号、订单号、标题会被判"已存在"）。
解决：yaml 里写**函数调用**，执行到那一刻才现算。

```yaml
title: "auto-${random_str(8)}"     # 每次跑生成一个新后缀
phone: "${gen_phone()}"
order_no: "${timestamp()}"
```

可用的函数都在 `common/functions.py`：`gen_phone()` / `timestamp()` / `timestamp_ms()` / `random_str(n)` / `uuid_hex()`。

原理三步（见 `common/context.py:: _lookup`）：
1. 正则发现占位符里带括号 → 判定为函数调用
2. `getattr(functions, 名字)` 去 `functions.py` 里找这个函数
3. 找到就调用，找不到就报"可用的有：xxx"

> 安全：只能调 `functions.py` 里定义的函数。yaml 里写 `${os.system(...)}` 不会被执行。

实测日志（连跑两次，值都不同）：
```
热加载 random_str(8) -> gq7opmib
热加载 random_str(8) -> c9r14f95
```

### 清理保障：中间失败也不留垃圾

**问题**：yaml 用例是顺序依赖的（创建 → 查询 → 删除）。
如果中间某条失败导致后面的"删除"没跑到，商品就残留在测试站上，越积越多。

**做法**：给用例加 `cleanup` 字段，框架登记下来，全部跑完后统一清理。

```yaml
  cleanup:
    method: DELETE
    path: /products/${product_id}
    headers: {Authorization: "Bearer ${token}"}
```

两个细节：
1. `runner.py` 把登记清理放在 **expect 断言之前** —— 这样即使断言失败抛异常，数据也已被记下
2. `conftest.py` 里用 `autouse=True` 的 session fixture 做收尾（不用在用例里写名字）

实测日志：
```
清理测试数据 DELETE /products/545 -> 200
清理测试数据 DELETE /products/546 -> 200
```

## 三条硬规矩（和 UI 项目一样）

1. **必须设超时** —— `HttpClient` 已经帮你做了，不要绕过它直接用 `requests.get`
2. **自己造的数据自己清** —— 创建类用例一律用 `try/finally` 删除
3. **断言要断言业务字段** —— 只断言状态码 200 是不够的，那只能证明"接口没崩"，
   证明不了"接口做对了"
