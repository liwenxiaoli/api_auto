# POST 接口压测全过程（写操作，含每一次判决）

> 与《GET 压测全过程-改动记录》同结构：**现象 → 判断 → 改了哪儿 → 结果**。
> 测试日期：2026-11-08 晚。被测：`POST /products`（INSERT + commit）。
> 所有数字都是本机实测，环境：AMD Ryzen 9 7945HX（32 逻辑核）、Windows 11、单进程 waitress。

---

## 阶段 0：为什么单独写一个压测脚本

**改了哪儿**：新建 `perf/locustfile_write.py`，与只读的 `perf/locustfile.py` 分开。

**为什么**：一个脚本里混着读和写，测出来的是"读写混合"——既不能和 GET 的 2491 RPS 对比，
也说不清瓶颈是读的还是写的。**一个文件只放一类任务**，数据才有意义。

```python
class ProductWriter(HttpUser):
    host = "http://127.0.0.1:5000"
    wait_time = between(0.1, 0.2)

    @task
    def create_product(self):
        payload = {"name": f"perf-{random.randint(1, 10**9)}", "price": random.randint(1, 100)}
        with self.client.post("/products", json=payload, catch_response=True) as resp:
            if resp.status_code != 201:
                resp.failure(f"期望 201，实际 {resp.status_code}，响应 {resp.text[:100]}")
```

两个刻意的设计：

| 写法 | 为什么 |
|---|---|
| `name` 带随机数 | 每次写入都不一样，压完可以直接在库里数出这轮写了多少条 |
| `catch_response=True` + 判 201 | 默认规则是"2xx 全算成功"，接口退化成返回 200 时你看不出来 |

**另外必须先清空表**：`POST /reset`（`curl.exe -X POST http://127.0.0.1:5000/reset`）。
表里数据量不一样，插入成本就不一样，两次结果不可比。

## 阶段 1：先做小压力标定

### 做法

### 判断

## 阶段 3：为什么小压力标定会把单次成本高估 2 倍

小压力（10 用户）时，两次写入之间隔了 100 多毫秒。**每次 commit 都是独立的一次 fsync，
磁盘空着，老老实实等它转一圈**——测出 6ms。

高压力（400 用户）时，commit 排着队来。操作系统的 I/O 调度会把相邻的落盘请求**合并成一批**，
一次 fsync 覆盖好几个事务。所以每次的**均摊**成本降到 3.06ms。

> **教训**：标定单次成本必须在**目标负载下**做，小压力测出来的数会系统性偏高。
> 这类"放大后才显现的效应"（批处理、缓存、连接池预热）是压测里最常见的坑。

现在三个数能互相验证了：

```
1 ÷ 327.20 = 3.06ms            ← 每次写入真实耗时
在途请求 = 327.20 × 1.047 = 342   ← 同一时刻有多少个请求在系统里
排队时长 = 342 × 3.06ms = 1.05s ≈ Med 1100ms   ← 闭口了
```

排队几乎占了 Med 的全部（1100ms 里 1097ms 是排队，只有 3ms 在干活）。
**排队不会降低吞吐，只会增加延迟**——这是饱和系统的标准形态。

## 阶段 4：400 vs 500，看是不是到顶了

### 结果

| 用户数 | RPS | Med | 在途 |
|---|---|---|---|
| 400 | 327.20 | 1100 ms | 342 |
| 500 | 318.01 | 1400 ms | 440 |

### 判断

`RPS` 基本持平（−2.8%，在测量噪声内），`Med` 涨 27%，在途请求 +98 ≈ 新增用户 100。

**判据（本节课第三次用）**：RPS 卡住不动 + Med 明显上涨 = 请求已经进入服务端，在排队。
多出来的 100 个用户一个都没多干活，全变成了队列长度。

但**这只排除了"请求进不来"，没排除"压测机自己到顶"**——因为客户端被 GIL 锁在单核上时，
表现完全一样（RPS 卡住、Med 上涨）。必须看 CPU 才能定案。

## 阶段 5：用任务管理器给两个进程"认人"

### 做法

压测进行中去任务管理器 → 进程，看两个 `python.exe`。

### 结果

| 进程 | CPU | 内存 | 磁盘 | 是谁 |
|---|---|---|---|---|
| Python #1 | 1.9% | 22.6 MB | **2.6 MB/秒** | mock 服务端 |
| Python #2 | 1.1% | 67.1 MB | 0 MB/秒 | locust 客户端 |

### 判断

**认人靠磁盘列，用反证法**：mock 每秒要处理 318 次 commit，必然持续写盘；locust 只发包，
一个字节都不写（没开 `--csv`）。所以有磁盘的那个是服务端。

**数字再验一次**：`2.6 MB/秒 ÷ 318 次/秒 = 8.2 KB/次`，正好是 SQLite WAL 一次 commit 的量级。
如果认反了，这条完全算不通。

**换算**：32 逻辑核，1 个核跑满 = 100 ÷ 32 = **3.1%**。

- 客户端 1.1% ≈ **0.35 个核**（远没到 1 核）→ 不是压测机瓶颈
- 服务端 1.9% ≈ **0.61 个核**（CPU 也没满）→ 它没在算，在等

### 结果

**318 RPS 是服务端瓶颈，且瓶颈不在 CPU，在等磁盘。**

## 阶段 6：干预实验前先写下预测

前面的结论全是**推断**。推断再自洽也不能算证据，必须**改动被怀疑的变量，看数字动不动**。

**改了哪儿**：`mock/app.py` 的 `get_conn()` 里临时加一行（WAL 必须先设，顺序不能反）：

```python
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("PRAGMA synchronous=NORMAL")   # ← 实验开关：commit 不等落盘
```

**先写预测**：如果 fsync 真是瓶颈，RPS 应大幅跳升（估计 700~1500），Med 大幅下降，
磁盘应从"持续 2.6MB/s"变成"一波一波地写"。

---

## 阶段 7：干预实验结果——归因成立

```
POST /products   56714 reqs  0(0.00%)  Avg 281  Min 0  Max 1904  Med 280   1139.43 req/s
```

| | synchronous 默认(FULL) | synchronous=NORMAL | 变化 |
|---|---|---|---|
| RPS | 318 | **1139** | **×3.58** |
| Med | 1400 ms | **280 ms** | ÷5 |
| Min | 45 ms | **0 ms** | — |
| 失败率 | 0% | 0% | — |

**预测命中**（1139 落在 700~1500 区间内）。

### 两个细节比总量更有说服力

1. **`Min` 从 45ms 变成 0ms**。45ms 是 fsync 落盘的物理下限，现在这个下限消失了——
   说明 commit 真的不再等盘。这是"fsync 被关掉"的直接指纹。
2. **只改了一行，吞吐 ×3.58**。如果之前的归因是错的，一行 PRAGMA 不可能有这个效果。

> 注意：`synchronous=NORMAL` 在断电时可能丢失最近几笔事务，**这是验证瓶颈的实验手段，
> 不是生产配置**。主动讲清这一点，面试反而加分。

## 阶段 8：700 用户把服务打崩了（Windows 512 上限）

### 现象

```
ValueError: too many file descriptors in select()
```

waitress 的 `wasyncore.poll` 崩在 `select.select()`，服务进程直接退出。

### 判断

**512 限制的是"并发连接数"，不是 RPS。**

Locust 每个用户持有一条 keep-alive 连接，发完不关。所以：

- 500 用户 = 500 条常驻连接（+ 监听 socket，约 505）→ **刚好卡在 512 下面，能跑通**
- 700 用户 = 700 条连接 → **直接超线，必崩**

推论：600 用户大概率也崩（600 > 512）。"加用户加压"这条路在本机走不通。

## 阶段 9：换加压方式——不动用户数，改用户"手速"

### 改了哪儿

`perf/locustfile_write.py` 里把 `wait_time = between(0.1, 0.2)` 改成 `between(0, 0.1)`。

**关键**：用户数不变（连接数不变，不会崩），但每个用户不再停顿，客户端压力翻倍。

### 结果

```
POST /products   57137 reqs  0(0.00%)  Avg 377  Min 9  Max 1834  Med 390   1150.27 req/s
```

| 条件 | RPS | Med | 在途 |
|---|---|---|---|
| NORMAL / 有 wait | 1139.43 | 280 ms | 320 |
| NORMAL / wait 归零 | **1150.27** | 390 ms | **434** |

### 判断（这是全篇最关键的一步）

客户端压力翻倍后：

- 在途请求 320 → 434（**+36%**）
- Med 280 → 390（**+39%**）
- RPS 1139 → 1150（**+1%**）

**并发加了一百多个，吞吐只加了 11 个。多出来的全变成队列了。**

这是饱和的标准签名。如果瓶颈在压测机，wait 归零后 RPS 应该跟着涨；它不涨，说明**瓶颈在服务端**。

### 结论

**1150 RPS 是服务端写操作的上限，不是压测机的上限。**

而 `1 ÷ 1150 = 0.87ms` 这次全是纯计算（Flask 解析 → sqlite3 序列化 → 写 WAL 缓冲），
fsync 已经不在里面了。**新的瓶颈是一个 Python 进程的 CPU/GIL**——和上午讲的 GIL 是同一件事。

## 阶段 10：收尾（写回默认配置）

1. 删掉 `PRAGMA synchronous=NORMAL` 那行（SQLite 默认就是 FULL，不用显式改成 FULL）
2. `wait_time` 改回 `between(0.1, 0.2)`
3. 重启服务，再跑一次 500 用户做回归，**应该回到约 318**

> 第 3 步是"整轮实验闭环"的证明：318 → 改一行 → 1139 → 加压 → 1150 → 删回 → 318。
> 同一个数能复现，比任何解释都硬。
>

## 附：可复用命令

```powershell
# 清表（每次开压前必做）
curl.exe -X POST http://127.0.0.1:5000/reset

# 基准压测
python -m locust -f perf/locustfile_write.py --headless -u 500 -r 250 -t 50s --only-summary

# 加压实验（先把 wait_time 改成 between(0, 0.1)）
python -m locust -f perf/locustfile_write.py --headless -u 500 -r 250 -t 50s --only-summary

# 认进程（看 CommandLine 里谁带 locust）
Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Select-Object ProcessId, CommandLine | Format-List

# 认服务端（5000 端口对应的 PID）
netstat -ano | findstr :5000
```

`-r` 的经验值：**用户数 ÷ 200 左右，让爬坡只占 2 秒**。爬坡期请求不走排队，会把 Avg 拉低
（本次 Avg 1047 < Med 1100 就是这个原因，不是算错了）。
