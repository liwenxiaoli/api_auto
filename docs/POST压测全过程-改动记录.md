# POST 接口压测全过程（写操作，含每一次判决）

> 与《GET 压测全过程-改动记录》同结构：**现象 → 判断 → 改了哪儿 → 结果**。
> 测试日期：2026-11-08 晚。被测：`POST /products`（INSERT + commit）。
> 所有数字都是本机实测，环境：AMD Ryzen 9 7945HX（32 逻辑核）、Windows 11、单进程 waitress。

---

## 阶段 0：为什么单独写一个压测脚本

**改了哪儿**：新建 `perf/locustfile_write.py`，与只读的 `perf/locustfile.py` 分开。

**为什么**：一个脚本里混着读和写，测出来的是"读写混合"——既不能和 GET 的 2491 RPS 对比，
也说不清瓶颈是读的还是写的。**一个文件只放一类任务**，数据才有意义。

```python
class ProductWriter(HttpUser):
    host = "http://127.0.0.1:5000"
    wait_time = between(0.1, 0.2)

    @task
    def create_product(self):
        payload = {"name": f"perf-{random.randint(1, 10**9)}", "price": random.randint(1, 100)}
        with self.client.post("/products", json=payload, catch_response=True) as resp:
            if resp.status_code != 201:
                resp.failure(f"期望 201，实际 {resp.status_code}，响应 {resp.text[:100]}")
```

两个刻意的设计：

| 写法 | 为什么 |
|---|---|
| `name` 带随机数 | 每次写入都不一样，压完可以直接在库里数出这轮写了多少条 |
| `catch_response=True` + 判 201 | 默认规则是"2xx 全算成功"，接口退化成返回 200 时你看不出来 |

**另外必须先清空表**：`POST /reset`（`curl.exe -X POST http://127.0.0.1:5000/reset`）。
表里数据量不一样，插入成本就不一样，两次结果不可比。

## 阶段 3：为什么小压力标定会把单次成本高估 2 倍

小压力（10 用户）时，两次写入之间隔了 100 多毫秒。**每次 commit 都是独立的一次 fsync，
磁盘空着，老老实实等它转一圈**——测出 6ms。

高压力（400 用户）时，commit 排着队来。操作系统的 I/O 调度会把相邻的落盘请求**合并成一批**，
一次 fsync 覆盖好几个事务。所以每次的**均摊**成本降到 3.06ms。

> **教训**：标定单次成本必须在**目标负载下**做，小压力测出来的数会系统性偏高。
> 这类"放大后才显现的效应"（批处理、缓存、连接池预热）是压测里最常见的坑。

现在三个数能互相验证了：

```
1 ÷ 327.20 = 3.06ms            ← 每次写入真实耗时
在途请求 = 327.20 × 1.047 = 342   ← 同一时刻有多少个请求在系统里
排队时长 = 342 × 3.06ms = 1.05s ≈ Med 1100ms   ← 闭口了
```

排队几乎占了 Med 的全部（1100ms 里 1097ms 是排队，只有 3ms 在干活）。
**排队不会降低吞吐，只会增加延迟**——这是饱和系统的标准形态。

## 阶段 4：400 vs 500，看是不是到顶了

### 结果

| 用户数 | RPS | Med | 在途 |
|---|---|---|---|
| 400 | 327.20 | 1100 ms | 342 |
| 500 | 318.01 | 1400 ms | 440 |

### 判断

`RPS` 基本持平（−2.8%，在测量噪声内），`Med` 涨 27%，在途请求 +98 ≈ 新增用户 100。

**判据（本节课第三次用）**：RPS 卡住不动 + Med 明显上涨 = 请求已经进入服务端，在排队。
多出来的 100 个用户一个都没多干活，全变成了队列长度。

但**这只排除了"请求进不来"，没排除"压测机自己到顶"**——因为客户端被 GIL 锁在单核上时，
表现完全一样（RPS 卡住、Med 上涨）。必须看 CPU 才能定案。

## 阶段 5：用任务管理器给两个进程"认人"

### 做法

压测进行中去任务管理器 → 进程，看两个 `python.exe`。

### 结果

| 进程 | CPU | 内存 | 磁盘 | 是谁 |
|---|---|---|---|---|
| Python #1 | 1.9% | 22.6 MB | **2.6 MB/秒** | mock 服务端 |
| Python #2 | 1.1% | 67.1 MB | 0 MB/秒 | locust 客户端 |

### 判断

**认人靠磁盘列，用反证法**：mock 每秒要处理 318 次 commit，必然持续写盘；locust 只发包，
一个字节都不写（没开 `--csv`）。所以有磁盘的那个是服务端。

**数字再验一次**：`2.6 MB/秒 ÷ 318 次/秒 = 8.2 KB/次`，正好是 SQLite WAL 一次 commit 的量级。
如果认反了，这条完全算不通。

**换算**：32 逻辑核，1 个核跑满 = 100 ÷ 32 = **3.1%**。

- 客户端 1.1% ≈ **0.35 个核**（远没到 1 核）→ 不是压测机瓶颈
- 服务端 1.9% ≈ **0.61 个核**（CPU 也没满）→ 它没在算，在等

### 结果

**318 RPS 是服务端瓶颈，且瓶颈不在 CPU，在等磁盘。**

## 阶段 6：干预实验前先写下预测

前面的结论全是**推断**。推断再自洽也不能算证据，必须**改动被怀疑的变量，看数字动不动**。

**改了哪儿**：`mock/app.py` 的 `get_conn()` 里临时加一行（WAL 必须先设，顺序不能反）：

```python
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("PRAGMA synchronous=NORMAL")   # ← 实验开关：commit 不等落盘
```

**先写预测**：如果 fsync 真是瓶颈，RPS 应大幅跳升（估计 700~1500），Med 大幅下降，
磁盘应从"持续 2.6MB/s"变成"一波一波地写"。

---

## 阶段 7：干预实验结果——归因成立

```
POST /products   56714 reqs  0(0.00%)  Avg 281  Min 0  Max 1904  Med 280   1139.43 req/s
```

| | synchronous 默认(FULL) | synchronous=NORMAL | 变化 |
|---|---|---|---|
| RPS | 318 | **1139** | **×3.58** |
| Med | 1400 ms | **280 ms** | ÷5 |
| Min | 45 ms | **0 ms** | — |
| 失败率 | 0% | 0% | — |

**预测命中**（1139 落在 700~1500 区间内）。

### 两个细节比总量更有说服力

1. **`Min` 从 45ms 变成 0ms**。45ms 是 fsync 落盘的物理下限，现在这个下限消失了——
   说明 commit 真的不再等盘。这是"fsync 被关掉"的直接指纹。
2. **只改了一行，吞吐 ×3.58**。如果之前的归因是错的，一行 PRAGMA 不可能有这个效果。

> 注意：`synchronous=NORMAL` 在断电时可能丢失最近几笔事务，**这是验证瓶颈的实验手段，
> 不是生产配置**。主动讲清这一点，面试反而加分。

## 阶段 8：700 用户把服务打崩了（Windows 512 上限）

### 现象

```
ValueError: too many file descriptors in select()
```

waitress 的 `wasyncore.poll` 崩在 `select.select()`，服务进程直接退出。

### 判断

**512 限制的是"并发连接数"，不是 RPS。**

Locust 每个用户持有一条 keep-alive 连接，发完不关。所以：

- 500 用户 = 500 条常驻连接（+ 监听 socket，约 505）→ **刚好卡在 512 下面，能跑通**
- 700 用户 = 700 条连接 → **直接超线，必崩**

推论：600 用户大概率也崩（600 > 512）。"加用户加压"这条路在本机走不通。

---

## 阶段 9：换加压方式——不动用户数，改用户"手速"

### 改了哪儿

`perf/locustfile_write.py` 里把 `wait_time = between(0.1, 0.2)` 改成 `between(0, 0.1)`。

**关键**：用户数不变（连接数不变，不会崩），但每个用户不再停顿，客户端压力翻倍。

### 结果

```
POST /products   57137 reqs  0(0.00%)  Avg 377  Min 9  Max 1834  Med 390   1150.27 req/s
```

| 条件 | RPS | Med | 在途 |
|---|---|---|---|
| NORMAL / 有 wait | 1139.43 | 280 ms | 320 |
| NORMAL / wait 归零 | **1150.27** | 390 ms | **434** |

### 判断（这是全篇最关键的一步）

客户端压力翻倍后：

- 在途请求 320 → 434（**+36%**）
- Med 280 → 390（**+39%**）
- RPS 1139 → 1150（**+1%**）

**并发加了一百多个，吞吐只加了 11 个。多出来的全变成队列了。**

这是饱和的标准签名。如果瓶颈在压测机，wait 归零后 RPS 应该跟着涨；它不涨，说明**瓶颈在服务端**。

### 结论

**1150 RPS 是服务端写操作的上限，不是压测机的上限。**

而 `1 ÷ 1150 = 0.87ms` 这次全是纯计算（Flask 解析 → sqlite3 序列化 → 写 WAL 缓冲），
fsync 已经不在里面了。**新的瓶颈是一个 Python 进程的 CPU/GIL**——和上午讲的 GIL 是同一件事。

---

## 阶段 10：收尾（写回默认配置）

1. 删掉 `PRAGMA synchronous=NORMAL` 那行（SQLite 默认就是 FULL，不用显式改成 FULL）
2. `wait_time` 改回 `between(0.1, 0.2)`
3. 重启服务，再跑一次 500 用户做回归，**应该回到约 318**

> 第 3 步是"整轮实验闭环"的证明：318 → 改一行 → 1139 → 加压 → 1150 → 删回 → 318。
> 同一个数能复现，比任何解释都硬。
>
> ✅ 已于 11-11 补跑：**322.42 RPS / Med 1400ms / 0 失败**，与改动前（318/1400）吻合，
> 差 1.4% 在噪声内。闭环成立。

## 阶段 11：新瓶颈判决（11-11 补充实验）

### 目的

验证阶段 9 的结论"1150 是服务端上限"里，那个上限到底是什么。原假设：单进程 CPU/GIL。

### 准备

临时加回 `PRAGMA synchronous=NORMAL`（复现高吞吐条件），重启服务，清表。

### 轮 1：基线（单 locust，500 用户，wait 归零）

```
POST /products   70026 reqs  0(0.00%)  Avg 296  Min 11  Max 2769  Med 300   1415.53 req/s
```

CPU 采样（每 2 秒一次，全程稳定）：**服务端 1.25 核，客户端 0.87 核**。

> ⚠️ 比上周五的 1150 高了 23%。原因：上周五那轮表里残留 5.7 万行数据、未清 WAL，
> 且是单次测量；今天是清表 + 背靠背。**单次测量 + 条件漂移可以差 20% 以上**，
> 只有同协议背靠背的对比才可信。对外口径改为"约 1.4k~1.5k"。

### 轮 2：判决（两个 locust，各 250 用户，合计仍是 500）

```
进程 A：737.94 req/s，Med 290ms
进程 B：738.56 req/s，Med 290ms
合计：1476.50 req/s（比基线 +4.3%）
```

CPU 采样：服务端 1.24 核（没变），两个客户端各 **0.48 核**。

### 判读：三个嫌疑全部排除

| 嫌疑 | 排除证据 |
|---|---|
| 压测机 | 客户端并行度翻倍只 +4.3%；每个客户端仅用 0.48 核（自己上限 1 核），远没到墙 |
| 服务端 CPU/GIL | 1.25 核未贴任何上限；**超过 1 核本身就证明 GIL 锁不死它**——sqlite3 的 C 代码执行时释放 GIL，4 线程可并行 |
| 磁盘 | NORMAL 模式无逐次 fsync；Min 11ms（对比 FULL 时 45ms） |

### 结论

**瓶颈是 SQLite 单写者锁**（当前唯一剩下的嫌疑）：整个数据库同一时刻只有一把写锁，
每次 commit 都要竞争它。等锁不耗 CPU、不占磁盘，任务管理器没有任何一列能显示它——
这是"看不见的瓶颈"，只能靠排除法定位。

定量：`1 ÷ 1476 = 0.68ms` ≈ 每次写入的持锁时间 → 写上限 ≈ **1.4k~1.5k RPS**。

### 修订

- ~~1150 是写上限~~ → **约 1.4k~1.5k**（上周五 1150 那轮条件不干净）
- ~~上限来自单进程 CPU/GIL~~ → **来自 SQLite 单写者锁**（待终验，见下）

## 阶段 12：终验——独立 DB 双进程（11-15）

### 目的

阶段 11 用排除法把嫌疑收敛到"SQLite 单写者锁"，但那仍是**推断**。本次直接动手拆掉
这个共享资源（两个服务进程各用独立 DB 文件），看吞吐是否随之翻倍——翻倍则归因成立。

### 改了哪儿

1. `mock/app.py`：DB 路径支持命令行第二参数（默认仍是 `shop.db`）
   ```python
   port = int(sys.argv[1]) if len(sys.argv) > 1 else 5000
   if len(sys.argv) > 2:
       DB = str(Path(sys.argv[2]).resolve())   # 必须在 init_db() 之前
   ```
2. `perf/locustfile_write.py`：删掉类属性 `host`，改用 `--host` 传（类属性优先级高于
   `--host`，留着死值命令行会被忽略）
3. 临时加回 `PRAGMA synchronous=NORMAL`（与阶段 11 基线同条件，否则测的是 fsync）

### 第一次跑：100% 失败，全部 2 秒超时

```
POST /products   5750 reqs  5750(100.00%)  Min 2007  Max 2081  Med 2007   116.83 req/s
错误：期望 201，实际 0，响应（空）
```

`status_code = 0` + 空响应 + 每条都卡 2000ms ⇒ **根本没拿到 HTTP 响应**，服务没在收请求。

排查三步：

| 检查 | 结果 | 说明 |
|---|---|---|
| `netstat -ano \| findstr :5000` | 无监听 | 服务进程压根没起来 |
| `ls mock/*.db` | 只有旧的 `shop.db` | 连 `init_db()` 都没执行 |
| `curl` 直连 | 502 | 本机有**系统代理**，localhost 请求被转走了 |

**真凶**：`mock/app.py` 第 109 行是
```python
if __name__ == "__&#8203;main__":
```
粘贴代码时把 HTML 实体 `&#8203;`（零宽空格）当普通文本贴进去了。语法合法、不报错，
但 `__name__ == "__&#8203;main__"` 恒为 False，**整个启动块从不执行，进程静默退出**。

> 教训：`python xxx.py` 一执行就退、不报错、端口不监听，先查 `__main__` 那行有没有脏字符。
> 用 `ASCII` 视野看一遍（`repr()` 打印该行）比肉眼可靠。

顺带一个坑：`curl` 走系统代理返回 502，压本地必须 `curl.exe --noproxy '*'`；
locust 侧用环境变量 `NO_PROXY=127.0.0.1,localhost`。

### 修好后：两个服务 + 两个客户端

| 进程 | PID | 角色 | 平均 CPU | 折合核 |
|---|---|---|---|---|
| 服务 A（5000 → `mock/a.db`） | 29408 | waitress | 1.27 | **1.27 核** |
| 服务 B（5001 → `mock/b.db`） | 23716 | waitress | 1.28 | **1.28 核** |
| 客户端 A | 18856 | locust | 0.92 | **0.92 核** |
| 客户端 B | 35912 | locust | 0.92 | **0.92 核** |

（22 个采样点，全程稳定；服务端 PID 与 `netstat` 里 5000/5001 的 LISTENING PID 完全一致）

```
服务 A：78024 reqs  0(0.00%)  Avg 105  Min 6  Max 945   Med 110   1578.26 req/s
服务 B：77345 reqs  0(0.00%)  Avg 106  Min 6  Max 2943  Med 110   1564.47 req/s
合计：3142.73 req/s
```

### 判读

| | 单服务 + 单 DB（阶段 11 轮 2） | 双服务 + 独立 DB | 变化 |
|---|---|---|---|
| 吞吐 | 1476.50 | **3142.73** | **×2.13** |
| Med | 290ms | **110ms** | ÷2.6 |

**结论成立：瓶颈是那把共享的写锁。** 如果限制来自磁盘物理 IO，分库不会有效果
（两个进程写的还是同一块盘）。现在把共享资源拆开、吞吐立刻线性翻倍，因果链闭合。

### 独立复现（同日 17:07，用户独立操作一遍）

| | 14:31（首次） | 17:07（复现） | 差异 |
|---|---|---|---|
| 服务 A | 1578.26 / Med 110 | 1568.09 / Med 87 | −0.6% |
| 服务 B | 1564.47 / Med 110 | 1591.82 / Med 79 | +1.7% |
| **合计** | 3142.73 | **3159.91** | **+0.5%** |
| 失败 | 0 | 0 | — |

换操作者、换时间、独立重跑，合计只差 **0.5%**（噪声内）——**这才是"可复现"的样子**，
也是回答"这数靠谱吗"最直接的一条证据。复现那轮 Med 更低（87/79），说明两个客户端启动更同步、
队列更短，数据质量反而更好。

### 边界（对外必须带上）

每个客户端 **0.92 核**，几乎贴着自己 1 核的上限（locust 日志里
`CPU usage above 90%!` 说的就是它自己这个进程，不是整机）。所以 3143 里有客户端成分，
**不能写成"服务端上限 3143"**。正确表述：

> 把 DB 拆成两个独立文件后，写吞吐由约 1.48k 提升到 **3.14k RPS（×2.13）**，
> 证明原上限来自 SQLite 单写者锁，而非 CPU 或磁盘。

要再往上，得先解决压测端（分布式 locust / wrk / hey），这属于另一条线。

### 收尾

`PRAGMA synchronous=NORMAL` 已删除，`mock/app.py` 回到默认 FULL 配置；
`mock/a.db`、`mock/b.db` 由 `.gitignore` 的 `mock/*.db` 自动忽略，不入库。

```powershell
# 清表（每次开压前必做）
curl.exe -X POST http://127.0.0.1:5000/reset

# 基准压测
python -m locust -f perf/locustfile_write.py --headless -u 500 -r 250 -t 50s --only-summary

# 加压实验（先把 wait_time 改成 between(0, 0.1)）
python -m locust -f perf/locustfile_write.py --headless -u 500 -r 250 -t 50s --only-summary

# 认进程（看 CommandLine 里谁带 locust）
Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Select-Object ProcessId, CommandLine | Format-List

# 认服务端（5000 端口对应的 PID）
netstat -ano | findstr :5000

# 终验：双服务 + 独立 DB（阶段 12）
python mock/app.py 5000 mock/a.db
python mock/app.py 5001 mock/b.db
curl.exe --noproxy "*" -X POST http://127.0.0.1:5000/reset
curl.exe --noproxy "*" -X POST http://127.0.0.1:5001/reset
# 两个 locust 要几乎同时起，否则时间窗错开
python -m locust -f perf/locustfile_write.py --host http://127.0.0.1:5000 --headless -u 250 -r 125 -t 50s --only-summary
python -m locust -f perf/locustfile_write.py --host http://127.0.0.1:5001 --headless -u 250 -r 125 -t 50s --only-summary

# 采样各进程核数（100% = 1 核）
$p1=@{}; Get-Process python -EA SilentlyContinue | %{$p1[$_.Id]=$_.TotalProcessorTime.TotalSeconds}
Start-Sleep 3
1..22 | %{ $p2=@{}; Get-Process python -EA SilentlyContinue | %{$p2[$_.Id]=$_.TotalProcessorTime.TotalSeconds};
  "{0}  {1}" -f (Get-Date -f HH:mm:ss), (($p2.Keys | ?{$p1.ContainsKey($_)} | %{"$_={0:N2}" -f (($p2[$_]-$p1[$_])/2)}) -join '  ');
  $p1=$p2; Start-Sleep 2 }
```

`-r` 的经验值：**用户数 ÷ 200 左右，让爬坡只占 2 秒**。爬坡期请求不走排队，会把 Avg 拉低
（本次 Avg 1047 < Med 1100 就是这个原因，不是算错了）。
