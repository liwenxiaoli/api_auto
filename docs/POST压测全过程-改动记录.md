# POST 接口压测全过程（写操作，含每一次判决）

> 与《GET 压测全过程-改动记录》同结构：**现象 → 判断 → 改了哪儿 → 结果**。
> 测试日期：2026-11-08 晚。被测：`POST /products`（INSERT + commit）。
> 所有数字都是本机实测，环境：AMD Ryzen 9 7945HX（32 逻辑核）、Windows 11、单进程 waitress。

---

## 阶段 0：为什么单独写一个压测脚本

**改了哪儿**：新建 `perf/locustfile_write.py`，与只读的 `perf/locustfile.py` 分开。

**为什么**：一个脚本里混着读和写，测出来的是"读写混合"——既不能和 GET 的 2491 RPS 对比，
也说不清瓶颈是读的还是写的。**一个文件只放一类任务**，数据才有意义。

```python
class ProductWriter(HttpUser):
    host = "http://127.0.0.1:5000"
    wait_time = between(0.1, 0.2)

    @task
    def create_product(self):
        payload = {"name": f"perf-{random.randint(1, 10**9)}", "price": random.randint(1, 100)}
        with self.client.post("/products", json=payload, catch_response=True) as resp:
            if resp.status_code != 201:
                resp.failure(f"期望 201，实际 {resp.status_code}，响应 {resp.text[:100]}")
```

两个刻意的设计：

| 写法 | 为什么 |
|---|---|
| `name` 带随机数 | 每次写入都不一样，压完可以直接在库里数出这轮写了多少条 |
| `catch_response=True` + 判 201 | 默认规则是"2xx 全算成功"，接口退化成返回 200 时你看不出来 |

**另外必须先清空表**：`POST /reset`（`curl.exe -X POST http://127.0.0.1:5000/reset`）。
表里数据量不一样，插入成本就不一样，两次结果不可比。

## 阶段 3：为什么小压力标定会把单次成本高估 2 倍

小压力（10 用户）时，两次写入之间隔了 100 多毫秒。**每次 commit 都是独立的一次 fsync，
磁盘空着，老老实实等它转一圈**——测出 6ms。

高压力（400 用户）时，commit 排着队来。操作系统的 I/O 调度会把相邻的落盘请求**合并成一批**，
一次 fsync 覆盖好几个事务。所以每次的**均摊**成本降到 3.06ms。

> **教训**：标定单次成本必须在**目标负载下**做，小压力测出来的数会系统性偏高。
> 这类"放大后才显现的效应"（批处理、缓存、连接池预热）是压测里最常见的坑。

现在三个数能互相验证了：

```
1 ÷ 327.20 = 3.06ms            ← 每次写入真实耗时
在途请求 = 327.20 × 1.047 = 342   ← 同一时刻有多少个请求在系统里
排队时长 = 342 × 3.06ms = 1.05s ≈ Med 1100ms   ← 闭口了
```

排队几乎占了 Med 的全部（1100ms 里 1097ms 是排队，只有 3ms 在干活）。
**排队不会降低吞吐，只会增加延迟**——这是饱和系统的标准形态。

## 阶段 4：400 vs 500，看是不是到顶了

### 结果

| 用户数 | RPS | Med | 在途 |
|---|---|---|---|
| 400 | 327.20 | 1100 ms | 342 |
| 500 | 318.01 | 1400 ms | 440 |

### 判断

`RPS` 基本持平（−2.8%，在测量噪声内），`Med` 涨 27%，在途请求 +98 ≈ 新增用户 100。

**判据（本节课第三次用）**：RPS 卡住不动 + Med 明显上涨 = 请求已经进入服务端，在排队。
多出来的 100 个用户一个都没多干活，全变成了队列长度。

但**这只排除了"请求进不来"，没排除"压测机自己到顶"**——因为客户端被 GIL 锁在单核上时，
表现完全一样（RPS 卡住、Med 上涨）。必须看 CPU 才能定案。

## 阶段 5：用任务管理器给两个进程"认人"

### 做法

压测进行中去任务管理器 → 进程，看两个 `python.exe`。

### 结果

| 进程 | CPU | 内存 | 磁盘 | 是谁 |
|---|---|---|---|---|
| Python #1 | 1.9% | 22.6 MB | **2.6 MB/秒** | mock 服务端 |
| Python #2 | 1.1% | 67.1 MB | 0 MB/秒 | locust 客户端 |

### 判断

**认人靠磁盘列，用反证法**：mock 每秒要处理 318 次 commit，必然持续写盘；locust 只发包，
一个字节都不写（没开 `--csv`）。所以有磁盘的那个是服务端。

**数字再验一次**：`2.6 MB/秒 ÷ 318 次/秒 = 8.2 KB/次`，正好是 SQLite WAL 一次 commit 的量级。
如果认反了，这条完全算不通。

**换算**：32 逻辑核，1 个核跑满 = 100 ÷ 32 = **3.1%**。

- 客户端 1.1% ≈ **0.35 个核**（远没到 1 核）→ 不是压测机瓶颈
- 服务端 1.9% ≈ **0.61 个核**（CPU 也没满）→ 它没在算，在等

### 结果

**318 RPS 是服务端瓶颈，且瓶颈不在 CPU，在等磁盘。**

## 阶段 6：干预实验前先写下预测

前面的结论全是**推断**。推断再自洽也不能算证据，必须**改动被怀疑的变量，看数字动不动**。

**改了哪儿**：`mock/app.py` 的 `get_conn()` 里临时加一行（WAL 必须先设，顺序不能反）：

```python
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("PRAGMA synchronous=NORMAL")   # ← 实验开关：commit 不等落盘
```

**先写预测**：如果 fsync 真是瓶颈，RPS 应大幅跳升（估计 700~1500），Med 大幅下降，
磁盘应从"持续 2.6MB/s"变成"一波一波地写"。

---

## 阶段 7：干预实验结果——归因成立

```
POST /products   56714 reqs  0(0.00%)  Avg 281  Min 0  Max 1904  Med 280   1139.43 req/s
```

| | synchronous 默认(FULL) | synchronous=NORMAL | 变化 |
|---|---|---|---|
| RPS | 318 | **1139** | **×3.58** |
| Med | 1400 ms | **280 ms** | ÷5 |
| Min | 45 ms | **0 ms** | — |
| 失败率 | 0% | 0% | — |

**预测命中**（1139 落在 700~1500 区间内）。

### 两个细节比总量更有说服力

1. **`Min` 从 45ms 变成 0ms**。45ms 是 fsync 落盘的物理下限，现在这个下限消失了——
   说明 commit 真的不再等盘。这是"fsync 被关掉"的直接指纹。
2. **只改了一行，吞吐 ×3.58**。如果之前的归因是错的，一行 PRAGMA 不可能有这个效果。

> 注意：`synchronous=NORMAL` 在断电时可能丢失最近几笔事务，**这是验证瓶颈的实验手段，
> 不是生产配置**。主动讲清这一点，面试反而加分。

## 阶段 8：700 用户把服务打崩了（Windows 512 上限）

### 现象

```
ValueError: too many file descriptors in select()
```

waitress 的 `wasyncore.poll` 崩在 `select.select()`，服务进程直接退出。

### 判断

**512 限制的是"并发连接数"，不是 RPS。**

Locust 每个用户持有一条 keep-alive 连接，发完不关。所以：

- 500 用户 = 500 条常驻连接（+ 监听 socket，约 505）→ **刚好卡在 512 下面，能跑通**
- 700 用户 = 700 条连接 → **直接超线，必崩**

推论：600 用户大概率也崩（600 > 512）。"加用户加压"这条路在本机走不通。

---

## 阶段 9：换加压方式——不动用户数，改用户"手速"

### 改了哪儿

`perf/locustfile_write.py` 里把 `wait_time = between(0.1, 0.2)` 改成 `between(0, 0.1)`。

**关键**：用户数不变（连接数不变，不会崩），但每个用户不再停顿，客户端压力翻倍。

### 结果

```
POST /products   57137 reqs  0(0.00%)  Avg 377  Min 9  Max 1834  Med 390   1150.27 req/s
```

| 条件 | RPS | Med | 在途 |
|---|---|---|---|
| NORMAL / 有 wait | 1139.43 | 280 ms | 320 |
| NORMAL / wait 归零 | **1150.27** | 390 ms | **434** |

### 判断（这是全篇最关键的一步）

客户端压力翻倍后：

- 在途请求 320 → 434（**+36%**）
- Med 280 → 390（**+39%**）
- RPS 1139 → 1150（**+1%**）

**并发加了一百多个，吞吐只加了 11 个。多出来的全变成队列了。**

这是饱和的标准签名。如果瓶颈在压测机，wait 归零后 RPS 应该跟着涨；它不涨，说明**瓶颈在服务端**。

### 结论

**1150 RPS 是服务端写操作的上限，不是压测机的上限。**

而 `1 ÷ 1150 = 0.87ms` 这次全是纯计算（Flask 解析 → sqlite3 序列化 → 写 WAL 缓冲），
fsync 已经不在里面了。**新的瓶颈是一个 Python 进程的 CPU/GIL**——和上午讲的 GIL 是同一件事。

---

## 阶段 10：收尾（写回默认配置）

1. 删掉 `PRAGMA synchronous=NORMAL` 那行（SQLite 默认就是 FULL，不用显式改成 FULL）
2. `wait_time` 改回 `between(0.1, 0.2)`
3. 重启服务，再跑一次 500 用户做回归，**应该回到约 318**

> 第 3 步是"整轮实验闭环"的证明：318 → 改一行 → 1139 → 加压 → 1150 → 删回 → 318。
> 同一个数能复现，比任何解释都硬。
>
> ✅ 已于 11-11 补跑：**322.42 RPS / Med 1400ms / 0 失败**，与改动前（318/1400）吻合，
> 差 1.4% 在噪声内。闭环成立。

## 阶段 11：新瓶颈判决（11-11 补充实验）

### 目的

验证阶段 9 的结论"1150 是服务端上限"里，那个上限到底是什么。原假设：单进程 CPU/GIL。

### 准备

临时加回 `PRAGMA synchronous=NORMAL`（复现高吞吐条件），重启服务，清表。

### 轮 1：基线（单 locust，500 用户，wait 归零）

```
POST /products   70026 reqs  0(0.00%)  Avg 296  Min 11  Max 2769  Med 300   1415.53 req/s
```

CPU 采样（每 2 秒一次，全程稳定）：**服务端 1.25 核，客户端 0.87 核**。

> ⚠️ 比上周五的 1150 高了 23%。原因：上周五那轮表里残留 5.7 万行数据、未清 WAL，
> 且是单次测量；今天是清表 + 背靠背。**单次测量 + 条件漂移可以差 20% 以上**，
> 只有同协议背靠背的对比才可信。对外口径改为"约 1.4k~1.5k"。

### 轮 2：判决（两个 locust，各 250 用户，合计仍是 500）

```
进程 A：737.94 req/s，Med 290ms
进程 B：738.56 req/s，Med 290ms
合计：1476.50 req/s（比基线 +4.3%）
```

CPU 采样：服务端 1.24 核（没变），两个客户端各 **0.48 核**。

### 判读：三个嫌疑全部排除

| 嫌疑 | 排除证据 |
|---|---|
| 压测机 | 客户端并行度翻倍只 +4.3%；每个客户端仅用 0.48 核（自己上限 1 核），远没到墙 |
| 服务端 CPU/GIL | 1.25 核未贴任何上限；**超过 1 核本身就证明 GIL 锁不死它**——sqlite3 的 C 代码执行时释放 GIL，4 线程可并行 |
| 磁盘 | NORMAL 模式无逐次 fsync；Min 11ms（对比 FULL 时 45ms） |

### 结论

**瓶颈是 SQLite 单写者锁**（当前唯一剩下的嫌疑）：整个数据库同一时刻只有一把写锁，
每次 commit 都要竞争它。等锁不耗 CPU、不占磁盘，任务管理器没有任何一列能显示它——
这是"看不见的瓶颈"，只能靠排除法定位。

定量：`1 ÷ 1476 = 0.68ms` ≈ 每次写入的持锁时间 → 写上限 ≈ **1.4k~1.5k RPS**。

### 修订

- ~~1150 是写上限~~ → **约 1.4k~1.5k**（上周五 1150 那轮条件不干净）
- ~~上限来自单进程 CPU/GIL~~ → **来自 SQLite 单写者锁**（待终验，见下）

## 阶段 12：终验——独立 DB 双进程（11-15）

### 目的

阶段 11 用排除法把嫌疑收敛到"SQLite 单写者锁"，但那仍是**推断**。本次直接动手拆掉
这个共享资源（两个服务进程各用独立 DB 文件），看吞吐是否随之翻倍——翻倍则归因成立。

### 改了哪儿

1. `mock/app.py`：DB 路径支持命令行第二参数（默认仍是 `shop.db`）
   ```python
   port = int(sys.argv[1]) if len(sys.argv) > 1 else 5000
   if len(sys.argv) > 2:
       DB = str(Path(sys.argv[2]).resolve())   # 必须在 init_db() 之前
   ```
2. `perf/locustfile_write.py`：删掉类属性 `host`，改用 `--host` 传（类属性优先级高于
   `--host`，留着死值命令行会被忽略）
3. 临时加回 `PRAGMA synchronous=NORMAL`（与阶段 11 基线同条件，否则测的是 fsync）

### 第一次跑：100% 失败，全部 2 秒超时

```
POST /products   5750 reqs  5750(100.00%)  Min 2007  Max 2081  Med 2007   116.83 req/s
错误：期望 201，实际 0，响应（空）
```

`status_code = 0` + 空响应 + 每条都卡 2000ms ⇒ **根本没拿到 HTTP 响应**，服务没在收请求。

排查三步：

| 检查 | 结果 | 说明 |
|---|---|---|
| `netstat -ano \| findstr :5000` | 无监听 | 服务进程压根没起来 |
| `ls mock/*.db` | 只有旧的 `shop.db` | 连 `init_db()` 都没执行 |
| `curl` 直连 | 502 | 本机有**系统代理**，localhost 请求被转走了 |

**真凶**：`mock/app.py` 第 109 行是
```python
if __name__ == "__&#8203;main__":
```
粘贴代码时把 HTML 实体 `&#8203;`（零宽空格）当普通文本贴进去了。语法合法、不报错，
但 `__name__ == "__&#8203;main__"` 恒为 False，**整个启动块从不执行，进程静默退出**。

> 教训：`python xxx.py` 一执行就退、不报错、端口不监听，先查 `__main__` 那行有没有脏字符。
> 用 `ASCII` 视野看一遍（`repr()` 打印该行）比肉眼可靠。

顺带一个坑：`curl` 走系统代理返回 502，压本地必须 `curl.exe --noproxy '*'`；
locust 侧用环境变量 `NO_PROXY=127.0.0.1,localhost`。

### 修好后：两个服务 + 两个客户端

| 进程 | PID | 角色 | 平均 CPU | 折合核 |
|---|---|---|---|---|
| 服务 A（5000 → `mock/a.db`） | 29408 | waitress | 1.27 | **1.27 核** |
| 服务 B（5001 → `mock/b.db`） | 23716 | waitress | 1.28 | **1.28 核** |
| 客户端 A | 18856 | locust | 0.92 | **0.92 核** |
| 客户端 B | 35912 | locust | 0.92 | **0.92 核** |

（22 个采样点，全程稳定；服务端 PID 与 `netstat` 里 5000/5001 的 LISTENING PID 完全一致）

```
服务 A：78024 reqs  0(0.00%)  Avg 105  Min 6  Max 945   Med 110   1578.26 req/s
服务 B：77345 reqs  0(0.00%)  Avg 106  Min 6  Max 2943  Med 110   1564.47 req/s
合计：3142.73 req/s
```

### 判读

| | 单服务 + 单 DB（阶段 11 轮 2） | 双服务 + 独立 DB | 变化 |
|---|---|---|---|
| 吞吐 | 1476.50 | **3142.73** | **×2.13** |
| Med | 290ms | **110ms** | ÷2.6 |

**结论成立：瓶颈是那把共享的写锁。** 如果限制来自磁盘物理 IO，分库不会有效果
（两个进程写的还是同一块盘）。现在把共享资源拆开、吞吐立刻线性翻倍，因果链闭合。

### 独立复现（同日 17:07，用户独立操作一遍）

| | 14:31（首次） | 17:07（复现） | 差异 |
|---|---|---|---|
| 服务 A | 1578.26 / Med 110 | 1568.09 / Med 87 | −0.6% |
| 服务 B | 1564.47 / Med 110 | 1591.82 / Med 79 | +1.7% |
| **合计** | 3142.73 | **3159.91** | **+0.5%** |
| 失败 | 0 | 0 | — |

换操作者、换时间、独立重跑，合计只差 **0.5%**（噪声内）——**这才是"可复现"的样子**，
也是回答"这数靠谱吗"最直接的一条证据。复现那轮 Med 更低（87/79），说明两个客户端启动更同步、
队列更短，数据质量反而更好。

### 边界（对外必须带上）

每个客户端 **0.92 核**，几乎贴着自己 1 核的上限（locust 日志里
`CPU usage above 90%!` 说的就是它自己这个进程，不是整机）。所以 3143 里有客户端成分，
**不能写成"服务端上限 3143"**。正确表述：

> 把 DB 拆成两个独立文件后，写吞吐由约 1.48k 提升到 **3.14k RPS（×2.13）**，
> 证明原上限来自 SQLite 单写者锁，而非 CPU 或磁盘。

要再往上，得先解决压测端（分布式 locust / wrk / hey），这属于另一条线。

`PRAGMA synchronous=NORMAL` 已删除，`mock/app.py` 回到默认 FULL 配置；
`mock/a.db`、`mock/b.db` 由 `.gitignore` 的 `mock/*.db` 自动忽略，不入库。

## 阶段 13：换 k6 突破客户端单核（11-15 晚）

### 背景

阶段 12 的结论带一个边界：每个 Locust 客户端 0.92 核、贴着 GIL 的 1 核上限，所以
"双进程 3143 RPS"里掺了客户端成分，无法断定服务端真实上限。要突破，得换一个
**不受 GIL 限制**的压测工具。选了 k6（Grafana 官方、Go 写、goroutine 自动摊多核、
官方发 Windows 预编译 zip，免安装）。

> 工具选择记录：wrk 无官方 Windows 版；hey 官方仓库只发源码不发布二进制（要自己装 Go 编译）；
> k6 官方发 `windows-amd64.zip`，winget 也有 `GrafanaLabs.k6`（但 MSI 安装被本机 UAC 拦，
> 退出码 1602，改走 gh-proxy 下载 zip 解压到 `tools/k6-v2.4.0-windows-amd64/k6.exe`）。

k6 压测脚本：`perf/write_test.js`（JavaScript，比 locustfile 还短；成功判据同 locust——
只有 `status === 201` 才算通过）。

### 轮 1：FULL 配置（默认），400 VU / 50s

```
http_reqs......: 16945  330.44 req/s
http_req_duration: avg=1.19s  med=1.19s  max=9.61s  p95=1.24s
http_req_failed: 0.00%（0 / 16945）
```

**关键发现 1**：k6 测 FULL 得 **330 RPS**，与 Locust 的 318 几乎一致。

> 意义：之前用"客户端 CPU 0.35 核未到顶"推断"318 是服务端上限"，现在换了一个
> **不受 GIL 限制**的多核工具独立重测，数字不变。两条独立路线（CPU 采样 / 换工具）
> 都指向同一答案 ⇒ **FULL 配置下 318~330 就是服务端真实上限，与客户端单核无关**。
> 这是"交叉验证"，比单一路径的推断硬得多。

### 轮 2：NORMAL 配置，400 VU / 50s

```
http_reqs......: 28642  570.11 req/s
http_req_duration: avg=699ms  med=720ms  max=3.01s  p95=932ms
http_req_failed: 0.47%（137 / 28642）
```

**关键发现 2**：出现 **137 次失败**，报错全是
`connectex: No connection could be made ... actively refused it`（连接被拒绝）。

> 这不是写锁冲突，也不是业务错误——是 **waitress 服务端扛不住 k6 的密集连接**：
> k6 的 400 VU 每个都反复新建 TCP 连接，瞬时连接数撞上 `connection_limit=1000`
> 或 accept 队列上限，那一瞬间新连接被拒。570 RPS 是"服务端被打崩前的峰值"，
> **不是 NORMAL 的真实上限**。

**关键发现 3（比数字重要）**：换掉慢的客户端后，瓶颈**转移**了。

> Locust 时代：客户端 0.92 核先到顶 ⇒ 我们以为 1139/1476 是服务端上限。
> k6 时代：客户端不再受限 ⇒ 服务端下一个隐藏瓶颈（waitress 单进程连接处理能力）
> 立刻暴露，直接 `connection refused`。
>
> 这说明：**压测工具的能力上限，决定了你能看到哪个瓶颈。** 工具弱，看到的是工具自己的墙；
> 工具强，才能把服务端真正的下一道墙逼出来。之前 Locust 测的 1139/1476，
> 其实根本没触到 waitress 的极限。

### 结论与修正

- FULL：318（Locust）≈ 330（k6），服务端真实上限，交叉验证成立 ✅
- NORMAL 的"服务端真实上限"**仍未测到**——之前 Locust 的 1139/1476 受客户端单核污染，
  需要先解决 waitress 的连接处理瓶颈（加大 `connection_limit`、或起多进程）后，
  才能用 k6 测出 NORMAL 的真实上限。

### 下一步（遗留）

要测 NORMAL 的真实上限，两条路任选：
1. **放大 waitress 的连接容量**：`connection_limit` 从 1000 调大（如 10000）、
   `backlog` 调大，让 k6 的密集连接不被拒
2. **起多进程 waitress**：Linux 下 gunicorn `-w N`；Windows 下手动起多个 waitress + 反向代理
   分摊连接

然后 k6 再压，才能看到 NORMAL 配置下服务端（而非客户端、也非连接层）的真实上限。

## 阶段 14：开放模型定速扫描——FULL 上限坐实 325 RPS（11-15 深夜）

### 为什么要换模型

阶段 13 虽然换了 k6，但仍用固定 VU 数（闭合模型）。闭合模型有个数学上的硬缺陷：

```
吞吐 = 用户数 ÷ 单次响应时间
```

延迟一涨，吞吐自动跟着跌，两者永远绑死。所以"吞吐卡住"既可能是服务端到顶，
也可能只是 VU 数量不够，**单点数据无法区分这两种情况**（阶段 13 的 330 就带着这个疑点，
当时判断为"疑似假上限"）。

开放模型（`constant-arrival-rate`）把发射速率交给时钟：每秒固定灌 N 个，不管服务端死活。
服务端处理不完时不会降速，而是表现为**延迟暴涨 + 请求被丢弃**，天花板就自己露出来了。

新增脚本 `perf/write_test_open.js`，`RATE` / `DURATION` 通过 `-e` 传入。

### 实验设计

- 单服务（5000，`shop.db`，`threads=4`，`connection_limit=10000`）
- FULL 态（`synchronous` 用默认值，`journal_mode=WAL`）
- 5 档扫描：250 / 300 / 330 / 360 / 400 每秒，各 40s，**每档前 `POST /reset` 清表**
- 服务 B（5001）已关闭，避免两个进程分摊磁盘写入

### 数据

| 目标 RPS | 实际达成 | med | p95 | 失败率 | dropped_iterations | VU 峰值 |
|---------|---------|-----|-----|--------|-------------------|---------|
| 250 | 249.32 | 2.66ms | 50.07ms | 0% | 0 | 4 |
| 300 | 299.69 | 2.98ms | 33.77ms | 0% | 0 | 5 |
| 330 | 329.54 | 7.25ms | 28.01ms | 0% | 0 | 12 |
| 360 | 324.72 | **1.09s** | 1.49s | 0% | **904** | 480（撞顶） |
| 400 | 322.22 | **1.47s** | 1.50s | 0% | **2616** | 480（撞顶） |

### 关键发现 1：临界点在 330 与 360 之间

- 250/300/330 三档：med 停在毫秒级（2.66 → 2.98 → 7.25ms），实际吞吐**精确跟随目标**
  （249.32/249、299.69/300、329.54/330），一个请求没丢 ⇒ 系统仍在线性区
- 360/400 两档：med 跳到 **1.09s / 1.47s（约 150 倍）**，吞吐锁死在 324.7 / 322.2，
  且出现 `dropped_iterations` ⇒ 已进入饱和区

⇒ **FULL 态单服务真实上限 ≈ 325 RPS（区间 322~330）。**

### 关键发现 2：`dropped_iterations` 才是"拒绝"，失败率是 0% 不代表没被拒

360 档目标 360、实际只完成 324.7，缺口 35/s。这 35/s 的请求**根本没被发出去**——
k6 的 VU 池被在途请求占满，超时的迭代被丢弃，所以既不算成功也不算失败，
`http_req_failed` 保持 0%。

> 教训：**只看 `http_req_failed` 会漏掉最严重的那类拒绝。**
> 开放模型下必须同时看 `dropped_iterations`（丢了多少请求）和 `vus` 是否撞到 `maxVUs`（池子是否被打穿）。

### 关键发现 3：过载后吞吐不升反降

360 档（324.7）比 330 档（329.5）反而低 1.5%。因为排队不是免费的：
在途请求变多 ⇒ 连接数、fd 集合、waitress 线程调度、内核 accept 队列都要多干活，
这些开销摊到每个请求上，有效处理能力被削掉一点。

> 所以"峰值吞吐"出现在刚好临界的 330 档，而不是过载的那两档。
> 容量规划如果取过载档的数字，会高估系统能力。

### 关键发现 4：Little's Law 反算在途数，与 VU 池上限吻合

`L = λ × W`（在途请求数 = 吞吐 × 响应时间）

- 360 档：324.72 × 1.09s ≈ **354 个在途**
- 400 档：322.22 × 1.47s ≈ **474 个在途**

脚本里 `maxVUs` 设的是 480，而 400 档恰好报
`Insufficient VUs, reached 480 active VUs and cannot initialize more`。
两个独立算出来的数字撞在一起（474 vs 480）⇒ 说明"在途请求把 VU 池吃光"这个归因是对的，
不是脚本参数没调好。

### 结论与修正

| 编号 | 原结论 | 现结论 |
|------|--------|--------|
| 1 | FULL 上限 318（Locust）/ 330（k6 闭合） | ✅ **成立**，开放模型扫描独立确认 ≈ 325 |
| 2 | 阶段 13 曾判"330 可能是闭合模型的假上限" | ❌ **收回**。330 档 med 仅 7.25ms、零丢弃，是真上限而非假象 |
| 3 | NORMAL 真实上限 1139/1476 | ⚠️ 仍作废（客户端单核污染 + waitress 连接层未解），**开放模型下尚未测过** |

> 方法论收获：**单点数字只能证明"这里有墙"，扫描才能证明"墙在哪、墙有多硬"。**
> 一个数字配上延迟行为（是否跳变）才算证据；孤立的一个 RPS 值，连自己是不是假上限都说明不了。

### 遗留（下一步）

1. **NORMAL 态开放模型扫描**（必须改 `mock/app.py` 加 `PRAGMA synchronous=NORMAL` 并重启）
   —— 现在三个数字里 FULL 已有硬证据、拆库 3143 有硬证据，**只有 NORMAL 这一格还空着**。
   简历若写"NORMAL 提升 3.58 倍"，该倍数是闭合模型算的，需用统一尺度重测才能站得住。
2. 提示：因 `threads=4` 且 Python 侧仍受限，`connection_limit=10000` 只是把连接层这堵墙推开，
   真正撞到的是 SQLite 写锁 + fsync 的处理能力，不是连接数。

### 可复用命令（Git Bash）

```bash
  curl.exe -s --noproxy "*" -o /dev/null -X POST http://127.0.0.1:5000/reset
```

## 阶段 15：NORMAL 态开放模型扫描——上限 1700 RPS（11-15 深夜）

### 预测（先写，后验证）

按「FULL 325 × 阶段 7 的 3.58 倍 ≈ 1160」推断，NORMAL 上限应在 **1100~1300**，
扫描档位定为 700 / 900 / 1100 / 1300 / 1500。

### 第一轮数据（累积库，`synchronous=NORMAL` 已生效）

| 目标 | 实际 | med | p95 | min | 判定 |
|------|------|-----|-----|-----|------|
| 700 | 699.99 | 527µs | 3.28ms | 0s | 线性 |
| 900 | 899.99 | 530µs | 3.35ms | 0s | 线性 |
| 1100 | 1099.82 | 525µs | 3.32ms | 0s | 线性 |
| 1300 | 1299.75 | 516µs | 3.30ms | 0s | 线性 |
| 1500 | 1499.94 | 520µs | 4.19ms | 0s | 线性 |

**预测当场被打脸**：1500 全部零丢弃、吞吐精确跟随目标，连边都没摸到。

### 关键发现 1：为什么预测错得这么远

3.58 是 `318 → 1139` 的比值，而 **1139 本身就是被 Locust 客户端单核限住的数字**。
拿一个受上游限制的数字去乘倍率，得到的必然还是受限制的数字。

真实因果链：

1. `synchronous=NORMAL` 之后 commit 不等 fsync 返回 ⇒ 写事务从毫秒级降到微秒级
2. 事务持锁时间跟着缩到微秒 ⇒ **原来的"单写者锁"这堵墙自己塌了**（锁还在，但没人排队）
3. `min=0s` 是 fsync 消失的直接物证（FULL 态那条 45ms 物理下限彻底没了）
4. 于是瓶颈不再是数据库，之前那些 1139 / 1415 / 1476 / 556 / 570 **全是客户端或连接层挡出来的**

### 第二轮：往上探（累积库）

| 目标 | 实际 | med | p90 | dropped | vus max | 判定 |
|------|------|-----|-----|---------|---------|------|
| 1600 | 1599.89 | 524µs | 3.71ms | 0 | **24** | 干净 |
| 1700 | 1334.17 | 354.83ms | 415ms | 10612 | **480** | 崩 |
| 1800 | 1574.53 | 303.59ms | 341ms | 6308 | **480** | 崩 |
| 1900 | 1180.80 | 382.72ms | 527ms | 21177 | **480** | 崩 |

三档缺口均**精确等于** `dropped_iterations`（10612 / 6308 / 21177），全部撞满 `maxVUs=480`。

> **异常点**：1800 完成 1574/s，比 1700 的 1334/s 还高 18%。灌得更多、完成得更多，
> 不可能是真实能力差异 ⇒ 说明过载区的单次测量不可信。

### 关键发现 2：双稳态——只有"健康"和"崩溃"两个状态

把所有档位的 med 排一遍：`520µs / 517µs / 522µs / 520µs` … 突然 `354ms / 446ms`。
**没有 50ms、100ms 这种中间值。** 系统只有两个吸引子，越过临界点就整体翻过去。

正反馈机制：

```
写入速率↑ → WAL 增长快 → checkpoint 变重
    ↑                        ↓
 排队更长 ← 写事务持锁时间变长 ← checkpoint 阻塞写入
```

一旦转起来，系统会自己维持在高延迟态，不会自行恢复 ⇒ 这就是为什么过载档即使 VU 池够也救不回来。

### 第三轮：复测（发现不可重复）

| 档位 | 吞吐 | med | vus max | 说明 |
|------|------|-----|---------|------|
| 1600 复测 A | 1598.76 | 517.8µs | 39 | 干净 |
| 1600 复测 B | 1599.90 | 522.4µs | 10 | 干净（两次差 0.07%） |
| 1650 | 1649.99 | 517.59µs | 54 | 干净 |
| **1700 重测** | **1699.20** | **520.29µs** | **24** | **干净！** |

**同一个 1700，第一次崩（1334/s、354ms），第二次干净（1699/s、520µs），差 27%。**

> 方法论：**线性区的数字可重复（六档误差 < 0.08%），过载区边缘的数字不可重复（同档差 27%）。**
> 所以"上限"必须复测 2~3 次取中位数，单次测量不能下结论。

### 第四轮：干净库定论

删库重启（`Remove-Item mock\shop.db*`）后，在空库上重跑三档：

| 目标 | 实际 | med | p95 | vus max | dropped | 判定 |
|------|------|-----|-----|---------|---------|------|
| 1650 | **1649.997** | 517µs | 4.33ms | **5** | 0 | 健康 |
| 1700 | **1698.008** | 522µs | 15.04ms | **15** | 0 | 健康 |
| 1800 | 1054.97 | 446.5ms | 587ms | **480** | 22058 | **崩溃** |

`vus max` 只有 5 和 15 ⇒ **压测端完全无关**，1800 的缺口 22058 精确等于 `dropped`，
责任 100% 在服务端。

### 关键发现 3：库的"脏度"会影响临界点

同一个 1700，在**累积库**上崩过一次，在**干净库**上两次都干净。
`DELETE FROM` 不回收文件空间，页进 freelist 反复复用，checkpoint 代价随历史增长。

⇒ 说"上限 1700"必须带条件：**干净库、无其他磁盘负载下**。

### 最终结论

| 配置 | 健康上限 | 上限处 med | 上限处 p95 |
|------|---------|-----------|-----------|
| FULL | 325 | 7.25ms（330 档） | 28ms |
| **NORMAL** | **1700** | **522µs** | **15.04ms** |

**325 → 1700 = ×5.23，同延迟从 7.25ms 降到 0.52ms（14 倍）。**

对简历的影响：原来写的「318 → 1139，×3.58」**严重低估**——它量的是当年被客户端单核卡住的 1139。
NORMAL 的真实能力是这个数的 1.5 倍。

### 遗留（下一步）

1. **瓶颈归因未做**。现在只测出"在哪里崩"，没测出"为什么崩"。
   已有强线索：**med 恒定 520µs、p95 从 4.33ms 涨到 15.04ms、max 出现 755ms~1.19s 尖刺** ——
   这是"间歇性整体卡顿"的典型形态，不像整体变慢（那 med 会一起涨），最像 **WAL checkpoint**。
   验证方法（一行 + 一档）：
   ```python
   conn.execute("PRAGMA wal_autocheckpoint=10000")  # 默认 1000 页
   ```
   若 p95 明显变薄 ⇒ checkpoint 是尾部尖刺来源；若不变 ⇒ 另找。
2. 若要做 1700 以上，需解决 `maxVUs=480` 与 Windows `select()` 512 句柄的矛盾，
   只能多进程服务 + 多客户端。

## 阶段 16：NORMAL 态瓶颈归因——checkpoint 验证（11-17 晚）

### 起点

阶段 15 留下的唯一未归因现象：NORMAL 态 med 恒定 522µs，p95 却从 4.19ms 涨到 15.04ms、
max 出现 755ms~1.19s 尖刺——**"整体没变慢，是间歇性整体卡顿"**。
唯一符合全部特征的候选：WAL checkpoint（攒够页数搬回主库的那一下会阻塞写入）。

### 第 0 轮：实验设计污染（反面教材，先记教训）

只加了 `wal_autocheckpoint=10000` 就开跑，结果 333.55/s、med 1.44s——**这是 FULL 态的数据**。
原因：阶段 15 收尾时删掉了 `synchronous=NORMAL`，第二天做实验忘了加回来，
两个变量同时变了（surgical FULL + checkpoint 参数），无法归因。
**识别特征：`min=5.14ms`（NORMAL 态 min 恒为 0s）+ 吞吐 333 ≈ FULL 上限 325。**

> 教训：干预实验动手前，先核对"当前生效的完整配置"，而不是"我记得我改过什么"。

### 第 1~3 轮：在临界档 1700 上做实验——全部作废

| 配置 | RATE | 吞吐 | med | dropped | 判定 |
|---|---|---|---|---|---|
| 10000 页 #1 | 1700 | 1205.54 | 402.56ms | 14458 | 崩 |
| 10000 页 #2 | 1700 | 1038.08 | 469.41ms | 19559 | 崩 |
| 500 页 | 1700 | 1048.16 | 209.84ms | — | 崩 |
| **默认 #1（回守基线）** | 1700 | **1048.51** | **446.35ms** | 19170 | **崩** |
| **默认 #2（回守基线）** | 1700 | **1699.90** | **516.7µs** | 0 | **健康** |

**决定性的一行是"回守基线"**：同一份代码、同样的干净库、相隔两分钟，默认配置跑出
1048/s（崩）和 1699.90/s（健康）两种结果。⇒ **1700 档本身就是临界点，结果接近掷硬币。**

⇒ 凡在 1700 上做的参数实验，全部无法归因（崩溃可能是参数造成，也可能是临界档随机落进崩溃支）。

> 教训一：**在临界点上做实验 = 在刀刃上量东西。** 双稳态系统在临界点只能给出两种结果，
> 噪声完全盖住小幅参数效应。要测参数，必须退到稳定健康区（med 恒 0.5ms、dropped 恒 0 的档位）。
> 教训二：**干预实验每次改完必须回守基线。** 不回守，就分不清"参数效应"和"环境漂移"。

### 第 4 轮：稳定区 1500 上的干净 A/B（本阶段唯一有效实验）

先确认 1500 当天仍稳定（1499.96/s、med 522.9µs、p95 5.23ms、dropped 0、vus max 16），
然后只改一个变量：

| 配置 | RATE | 吞吐 | med | p90 | p95 | max |
|---|---|---|---|---|---|---|
| 默认（1000 页） | 1500 | 1499.96/s | 522.9µs | 3.15ms | 5.23ms | 314.19ms |
| **wal_autocheckpoint=10000** | 1500 | 1499.98/s | 520.1µs | **1.06ms** | **2.59ms** | **168.32ms** |

**吞吐与 med 完全不变，尾部全线减半：p95 ÷2、p90 ÷3、max ÷2。**

### 结论（可对外讲的版本）

1. **checkpoint 假设证实**：checkpoint 触发频率 ÷10 ⇒ 尾部延迟 ÷2~3，吞吐无损。
   这是"改一个参数 → 尾部可预测地变化"的因果证据，不是相关。
   NORMAL 态的尾部尖刺来源就是 WAL checkpoint。
2. **`wal_autocheckpoint=10000` 是稳定区的有效优化**（p95 5.23→2.59ms，吞吐不变），
   但**仅在稳定区成立**；在临界档 1700 它既没把系统压垮也没救回来——无法归因。
3. **临界档上不可做参数实验**（同配置双结果，掷硬币）；**崩溃态数字不能当能力**（1205/1038/1048 均为崩溃残值）。
4. 三次预测全部落空的复盘：机制想对了（checkpoint 阻塞写入），**主导项判断错了**——
   一直默认"单次变重"会主导，实际在稳定区"次数减少"主导。
   预测错不可怕，**没有对照跑才是真正让实验作废的原因**。

### 遗留

1. 1700 临界点是否真实存在（还是纯环境随机），需要在安静环境复测多天才能定论；
2. `wal_autocheckpoint=10000` 在 1600（更靠近临界点）是否仍安全，未测；
3. 本次实验全部在 `synchronous=NORMAL`（实验开关）下进行，与生产 FULL 态结论不可混用。

```powershell
python -m locust -f perf/locustfile_write.py --host http://127.0.0.1:5001 --headless -u 250 -r 125 -t 50s --only-summary

# 采样各进程核数（100% = 1 核）
$p1=@{}; Get-Process python -EA SilentlyContinue | %{$p1[$_.Id]=$_.TotalProcessorTime.TotalSeconds}
Start-Sleep 3
1..22 | %{ $p2=@{}; Get-Process python -EA SilentlyContinue | %{$p2[$_.Id]=$_.TotalProcessorTime.TotalSeconds};
  "{0}  {1}" -f (Get-Date -f HH:mm:ss), (($p2.Keys | ?{$p1.ContainsKey($_)} | %{"$_={0:N2}" -f (($p2[$_]-$p1[$_])/2)}) -join '  ');
  $p1=$p2; Start-Sleep 2 }
```

`-r` 的经验值：**用户数 ÷ 200 左右，让爬坡只占 2 秒**。爬坡期请求不走排队，会把 Avg 拉低
（本次 Avg 1047 < Med 1100 就是这个原因，不是算错了）。
