## 二、核心模型：双通道

```
        ┌───────────── 通道 A：HTTP ─────────────┐
用例 →  │ requests → Flask 代码 → 响应 201/200    │ → 接口断言
        └───────────────────────────────────────┘
        ┌───────────── 通道 B：sqlite3 ──────────┐
用例 →  │ query_one() → 直接翻 shop.db 文件       │ → 数据库断言
        └───────────────────────────────────────┘
```

**通道 B 存在的唯一理由**：通道 A 的回答者是接口代码，代码可以撒谎。
（第 2 课实测：注释掉 `conn.commit()`，接口照样返回 201 并发了一个 id。）

> 接口断言 = 听服务员说"菜做好了"；数据库断言 = 亲自去厨房看盘子。

## 三、三条用例与它们的意义

| # | 用例 | 接口断言 | 数据库断言 | 验的是什么 |
|---|---|---|---|---|
| 1 | 创建商品后数据库里应有该记录 | 201 | `SELECT ... WHERE id=1` → `['小米15', 4999.0, 30]` | 数据**真的进去了**，且字段对得上 |
| 2 | 删除商品后数据库里应查不到 | 200 | 同一条 SQL → 查不到（`expect: null`） | 数据**真的没了** |
| 3 | 删除不存在的商品应返回 404 | 404 | `WHERE id=99999` → 查不到 | 异常路径的**接口语义**正确 |

第 3 条是**异常用例**，简历上单独值一行。

### 见红验收（必须做过才算数）

- 第 2 条 `expect: null` 改成 `expect: [1, 小米15]` → 报
  `AssertionError: 期望数据库里查得到记录，实际一条都没查到` ✅
- 绿 → 红 → 绿 走完整圈，证明断言不是"假绿"

## 四、简历怎么写

### 项目描述（放在 api_auto 那一栏）

> **api_auto** —— 基于 `requests + pytest + YAML` 的接口自动化框架，32 条用例全部数据驱动。
> 自建 Flask mock 服务支撑**数据库校验**，实现接口断言与数据库断言双通道。

### 要点（4 条，从强到弱）

1. 自建 Flask + SQLite mock 服务，使被测对象由黑盒变白盒，
   支撑数据库校验（公开 API 无法直连数据库，只能做接口断言）
2. 实现**接口断言 + 数据库断言双通道**，可捕获"接口返回成功但数据未落库"类缺陷，
   并通过破坏实验（去掉 `commit`）验证其有效性
3. 数据库断言采用 yaml 声明式配置（`db_assert.sql` 支持 `${变量}` 渲染，
   `expect: null` 表示期望查不到）；**未配置 db_path 的环境自动跳过**，
   不侵入既有 29 条用例
4. 本地 mock 使该类用例脱离公网依赖，单次运行 **0.16s**（公网环境仅登录即需 1s+），
   可稳定接入 CI

### 面试可能被追问的 5 个问题

**Q1：为什么不直接连测试环境的数据库？**
> 公开练手站的数据库在对方服务器上，没有连接权限。真实项目里测试环境通常可以连，
> 但为了仓库自包含（面试官 clone 下来能跑通），我选择内置一个 mock 服务。

**Q2：数据库断言会不会让用例变慢/不稳定？**
> 会引入耦合，所以做了两点控制：一是 `db_path` 没配的环境直接跳过（向后兼容），
> 二是连接加了 `timeout=10` 应对 SQLite 写锁。写 SQL 只用 `?` 占位符，避免注入。

**Q3：`expect: null` 为什么能表示"期望查不到"？**
> YAML 的 `null` 读到 Python 是 `None`，而 `fetchone()` 查不到时返回的正是 `None`，
> 两者语义天然咬合，所以断言写成 `assert row is None`。

**Q4：怎么证明你的数据库断言不是"永远绿"？**
> 做过见红验收：把 `expect: null` 改成期望具体值后，用例确实报红，
> 报错信息还能直接定位到 SQL 和数据。见过红的断言才可信。

**Q5：为什么 `cleanup` 登记在断言之前？**
> 万一后面断言失败抛异常，清理任务也已经被记下来了，测试结束时照样删除，
> 不会把造出来的数据脏在库里（见 `runner.py` 第 94 行注释）。

## 五、踩过的坑（真踩过，不是抄的）

| 现象 | 原因 / 修法 |
|---|---|
| 接口 201 但库里没数据 | 服务端漏了 `conn.commit()`（破坏实验） |
| `database is locked` / `unable to open database file` | 同时开了多个 mock 服务进程抢同一个 `shop.db`，只留一个 |
| 请求打到公网、POST /products 返回 500 | 忘了加 `--env=mock`（看日志第一行"环境 = ?"） |
| `405 Method Not Allowed` | 路径对但方法没注册（`/products/<int:pid>` 只登记 DELETE） |
| `TypeError: 'NoneType' object is not subscriptable` | 用 `data=` 发、`get_json()` 收到 None |
| UPDATE 后 `fetchone()` 拿到 None | 改数据的语句不产生结果集，只有 SELECT 才有 |
| teardown `DELETE /products/1 -> 404` | 第一条 cleanup 重复删已被删除的数据，**保留**更稳妥（单独跑第一条时不脏库） |
