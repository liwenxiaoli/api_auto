# 项目讲解六问（面试话术底稿）

> **用法**：闭卷讲，讲不下去再翻回来。目标不是"看懂"，是**不看稿子能连着说完**。
> 六题对应六种能力：执行链路 / 底层机制 / 设计取舍 / CI 判据 / 断言分工 / 批判性思考。
> 每题的「标准答案」是口语稿，不是书面语 —— 照着念一遍，再换成自己的词。

## 第 1 问：一条用例是怎么跑起来的？

> 考官想听的是：你知不知道 pytest 的运行机制，还是只会"点绿色三角形"。

### 标准答案（约 90 秒）

分三个阶段讲。

**第一个阶段是 import。** `test_product.py` 一被 pytest 导入，模块级那行 `CASES = load_cases("product_cases.yaml")` 就执行了，yaml 被读成一个 list，每个元素是一条用例的 dict。注意这时候**一条用例都还没跑**，只是数据准备好了。

**第二个阶段是收集。** `@pytest.mark.parametrize("case", CASES)` 让 pytest 按 list 的长度生成 8 个测试项，每个测试项记着自己用第几个元素。所以报告里能看到 8 条同名用例，靠参数 id 区分。

**第三个阶段是执行。** pytest 先解析测试函数的签名：

```python
def test_product(self, client, ctx, case, existing_product):
```

它拿这几个参数名去 fixture 表里查 —— `client`、`ctx`、`existing_product` 都是这么注入的，只有 `case` 来自 parametrize。**按名字查表，不是按位置传**，所以参数名写错一个字母就报 `fixture 'xxx' not found`。

参数齐了才真正调用函数体，而函数体只有一行：`run_case(client, case, ctx)`。

**run_case 内部是固定的 7 步：**

```
① 渲染占位符（params / json / headers）
② client.request 发出去（渲染 path、拼 base_url、session、timeout、日志）
③ 断言状态码
④ extract 提取 → 存进变量池
⑤ 登记 cleanup（在断言之前，断言失败也照删）
⑥ 断言 schema
⑦ 断言 expect → 断言数据库
```

**一句话总结**：yaml 只描述"调什么、期望什么"，执行逻辑全在 `run_case` 里，所以加场景只改 yaml，代码一行不动。

### 可能被追问

**Q：`existing_product` 是什么？为什么要它？**
A：前置数据 fixture，session 级只造一次。有了它，「查询刚创建的商品」这条用例单独用 `-k` 挑出来也能跑通，不用再靠「创建商品」那条先执行过。**这是根治顺序依赖的办法**。

**Q：`-n 4` 并发的时候，这个 fixture 会造几次数据？**
A：4 次。因为 xdist 是开进程不是开线程，每个 worker 内存独立，session 级 fixture 在**每个 worker 里各跑一次**。所以并发跑要确保 fixture 造的数据互相不冲突（比如标题带随机串）。

### 常见错法

只说"load_cases 读数据 → 传给 run_case"，**漏掉 fixture 注入**。这是 pytest 最核心的机制，漏了就等于不知道 pytest 怎么跑的。

## 第 2 问：`${token}` 是怎么变成真实 token 的？

> 考官想听的是：变量池这个东西是"施了魔法"还是有清晰的来源和替换时机。

### 标准答案（约 60 秒）

三件事要讲清：值从哪来、谁替换、什么时候替换。

**值从两个地方来：**

1. `init_context`（autouse fixture）在测试会话开始时登录一次，把 `access_token` 存进变量池。**yaml 里凭空写 `${token}` 能用，是因为有人替你登录了**，不是魔法。
2. 用例的 `extract` 步骤：把前面响应里的值（比如 `product_id`）存进池子。

**替换由 `ctx.render()` 执行**，被调用的位置有两处：

- `run_case` 渲染 `params` / `json` / `headers`
- `client.request` 渲染 `path`

这就是为什么 path 里的 `${product_id}` 也能生效 —— 那是 client 干的，不是 run_case 干的。

**时机是在 `requests` 真正发出去之前。** 发出去的是已经替换好的字符串，请求本身完全不知道有占位符这回事。

**render 内部**：正则扫到 `${...}` 就抓出来，先按名字查池子（`_lookup`），池子里没有再去找 `functions` 模块里的同名函数现算 —— 这就是 `${random_str(8)}` 的来源。

### 可能被追问

**Q：池子里没有这个变量会怎样？**
A：看实现。现在是把原字符串原样留着（或抛错，取决于 `_lookup`）。**设计上应该抛错**——拼错变量名还静默发出去，是最难查的 bug。

**Q：池子是 session 级的，那并发跑会不会串数据？**
A：不会串，但会**各自独立**。每个 worker 一个进程一个池子，所以 worker A 里 extract 的变量，worker B 看不见。这就是为什么用例之间不能有跨进程的隐式依赖。

### 常见错法

只说"ctx 建池子、client 挂上池子"，**没答"值从哪来"和"谁替换"**——而这两件才是题目问的。

## 第 3 问：数据库校验为什么必须单独搞 mock 环境？

> 考官想听的是：你能不能分清"不方便"和"不可能"。

### 标准答案（约 70 秒）

三层原因，从硬到软。

**第一层：连不上（物理不可能）。**
`db_path` 这个配置项只有 mock 环境配了。其他环境读到的 `settings.db_path` 是 `None`，`assert_db` 第二道门直接 `return`。公网的数据库不在我手上，没地址、没账号、没端口 —— 这不是"不方便"，是**做不到**。

**第二层：就算连上，表结构也不一样。**

| 我的 mock（自己 `CREATE TABLE` 写的） | escuelajs 公网 |
|---|---|
| `id, name, price, stock` | `id, title, price, description, category_id, images` |

我的 SQL 是 `SELECT name, price FROM products`，打到公网库直接 `no such column: name`。**表都不认识，还断言什么。**

**第三层：就算结构一样，数据也不可控。**
公网数据随时被别人改、被别人删。硬编码 `expect: [小米15, 4999]`，明天别人改个价我就红。所以公网的 32 条只断言**结构和关系**（`type: str`、`not_empty`、`contains: Shoes`），从不断言具体值。

**最本质的一句话：不是"环境不同"，是"被测对象不同"。**
32 条测的是 escuelajs 这个真接口；3 条测的是我自建的 Flask + SQLite，**接口和数据库都是我写的**。测两个不同的系统，本来就不该混在一个环境里跑。

marker 只是执行手段 —— 让同一套代码分两次跑、各带各的 `--env`，它不是原因。

### 可能被追问

**Q：那为什么不给公网也配个 db_path，硬跑一下？**
A：就算搞到只读权限，表结构对不上，SQL 必然报错；就算结构碰巧对上，数据被别人改，断言也是随机红。**这种"能跑但不可靠"的测试比没有更坏**，因为它会训练你忽略红色。

**Q：`expect: null` 是什么意思？**
A：表示"期望查不到"。⚠️ 这里有个坑：**忘写 expect 也会被当成 null**，于是"期望查不到"和"没写"变成同一个行为，会假绿。这是我列进重构清单的第一项。

### 常见错法

只答"权限不够"。会被追问"那给你权限就行了？"——真正答案是**表结构 + 数据可控性都不支持**。

## 第 4 问：CI 为什么要分冒烟和回归两层？

> 考官想听的是：你能不能说出**可操作的判据**，而不是"重要的 / 不重要的"。

### 标准答案（约 60 秒）

判据是一句话：

> **它挂了，别的用例还值不值得看？**

- 不值得看 → **冒烟**（它红了，后面的绿都是假的，必须先拦住合并）
- 还值得看 → **回归**（它是个叶子，挂了自己承担，晚点知道就行）

再压缩成四个字：**是不是前置**。

拿我的项目举例：登录成功挂了，所有要 token 的用例全没意义；商品列表挂了，所有查详情的全没意义 —— 所以它们是冒烟。「商品详情」重要不重要？重要，但**没有别的用例依赖它**，它是叶子，进回归就够了。

还有第二层判据：**误报的代价。**

冒烟要用来拦合并（branch protection），一旦误报 PR 被卡住，代价很高 → 所以只放**最稳的**用例，宁可少。回归只通知不拦合并 → 所以可以放全量、可以带 `--reruns`。

**落到实现**：34 条用例按 marker 切两层，不是两套代码。`smoke.yml` 在 push/PR 时跑 5 条（约 15 秒），`api-test.yml` 每天定时跑全量。

### 可能被追问

**Q：回归挂了怎么处理？**
A：只通知，不动合并门禁。因为全量里有数据库校验、有公网抖动，误报率高。**能用来拦合并的集合，必须误报率极低**，否则大家会习惯性忽略红色，门禁就废了。

**Q：为什么不把全量放 push 里跑？**
A：两个原因：一是时间（虽然并发后只有 13 秒，但公网抖动时带重试会拖很久），二是**噪声**。push 时跑全量，开发者会被跟自己改动无关的红色打断，久了就不看了。

### 常见错法

说"重要的进冒烟、不重要的进回归"。被追问"什么叫重要"就答不上。要立刻能说出「**挂了会阻断其他用例的那几条**」。

## 第 5 问：`schema` 和 `expect` 各保护什么？

> 考官想听的是：你知不知道自己在验证什么，以及验证的**盲区**在哪。

### 标准答案（约 60 秒）

区别不在"验什么"，在"**验多少**"。

- **`schema` 一次管整份响应**：20 个字段、3 层嵌套，一份规则全扫一遍 —— 这是**普查**
- **`expect` 只管家点名的字段**：你写了 `$.price` 才验 price，没写的字段它**当作不存在** —— 这是**抽查**

举个具体场景：「后端把 `price` 字段删了」。

- `expect` 里如果没点名 price，**照样绿**
- `schema` 里有 `required: ["id","title","price"]`，**立刻红**

所以：

> **`expect` 只检查你写出来的，`schema` 检查你没写出来的。**

这就是为什么 schema 能抓"后端偷偷删字段"，而 expect 一辈子抓不到 —— 字段都没了，你根本没机会写它。

**代价**：schema 需要维护一份 json 文件，改契约要同步改文件；expect 写一行就管一个字段。所以我的做法是**关键接口挂 schema 做普查 + 少量 expect 做重点抽查**。

### 可能被追问

**Q：那 schema 是不是可以完全替代 expect？**
A：不能。schema 只能表达"结构对不对"，表达不了"业务对不对"。比如「按标题搜 Shoes，返回的每条 title 都必须包含 Shoes」—— 这是业务规则，schema 写不了（能写正则但没法跟检索词联动）。**结构归 schema，业务归 expect。**

**Q：schema 有没有失效的情况？**
A：有三种，我今天都踩过：

| 写法 | 结果 | 原因 |
|---|---|---|
| `"require"` 少个 d | 绿 | 关键字不认识，当没写 |
| `required` 写在数组层（不套 `items`） | 绿 | 该关键字只对 object 生效，对数组跳过 |
| 只写 `properties` 不写 `required` | 绿 | 字段缺失时无值可查 |

共同原因：**jsonschema 遇到"管不了"的情况一律跳过，从不报错**。所以铁律是：**schema 写完必须拿一份故意违规的数据跑一次，它必须红。**

### 常见错法

说"schema 管类型、expect 管值"。两个都窄了 —— schema 也管"字段在不在"（required），expect 也能验类型（`{type: str}`）。

## 第 6 问：这个框架让你从头再写一遍，你会改哪三处？

> 考官想听的是：**批判性思考**。只会夸自己项目的人，通常没真读自己的代码。

### 标准答案（约 90 秒）

三处，都在"静默失效"这个主题上。

**第一处：`db_assert` 的 `expect: null` 有歧义。**

`null` 现在意思是「期望查不到」。但用户**忘写** `expect` 时，`conf.get("expect")` 也返回 `None`，被当成「期望查不到」，断言 `row is None` —— **假绿**。同一个 `None` 承担了"缺省"和"期望空"两个含义，这是设计缺陷。

改法：换成显式关键字 `expect_no_row: true`，或者让 `expect` 必填，没写就报配置错误。

**第二处：yaml 用例数据本身没有校验。**

`data/*.yaml` 是自由格式，字段名写错（`expect_status` 打成 `expect_stats`）会怎样？大概率 `KeyError`，报错指向 `runner.py` 第 89 行，跟你写的 yaml 八竿子打不着；更糟的是有些字段是 `.get()` 读的，写错了**静默忽略**，用例照绿。

改法：定义 `case.schema.json`，在 `load_cases` 里先校验每条用例数据的结构，写错字段名当场报错。**这是"用工具保护工具"** —— 项目里已经在用 jsonschema 校验响应，反过来校验自己的测试数据很自然。

**第三处：跳过要留痕。**

现在有三处静默跳过：`db_assert` 没写、环境没配 `db_path`、`schema` 没写。单看每处都合理（向后兼容），合起来的问题是：**跑完 32 条全绿，但你不知道哪几条其实少验了东西。**

改法：跳过的用例名收集起来，session 结束时打一条汇总，或者写进 Allure 的环境信息。让"我没验"这件事**可见**。

### 可能被追问

**Q：这三处有什么共同点？**
A：都是"失败没有声音"。前两处是**该红没红**，第三处是**该说没说**。工程上最难查的从来不是红，是绿得没有理由。

## 30 秒电梯版（自我介绍时用）

> 我有一个接口自动化项目，用 `requests + pytest + yaml` 搭的，34 条用例全部数据驱动 ——
> yaml 只描述"调什么、期望什么"，执行逻辑固定在 runner 里，所以加场景只改 yaml。
>
> 做了三件我觉得有价值的事：
> **一是三层校验**：状态码 → 结构契约（JSON Schema）→ 字段断言 → 数据库直连查库，接口说成功不一定真落库；
> **二是 CI 分层**：冒烟 5 条在 push 时跑，回归全量每天定时跑，判据是"这条挂了后面的还值不值得看"；
> **三是防假绿**：每条断言我都亲手让它红过一次，因为断言从来没红过，跟不存在没区别。

## 金句表（背下来，面试能直接用）

| 场景 | 一句话 |
|---|---|
| 分层判据 | 它挂了，别的用例还值不值得看？值得 → 回归；不值得 → 冒烟 |
| schema vs expect | expect 只检查你写出来的，schema 检查你没写出来的 |
| 断言的可信度 | 从来没红过的断言，跟不存在没区别 |
| 静默失效 | jsonschema 遇到管不了的情况一律跳过，从不报错 |
| 数据库校验的意义 | 接口说"菜做好了"，数据库说"盘子里真有菜" |
| 顺序依赖 | 前置数据 fixture 是根治顺序依赖的办法，`-k` 挑一条也能跑通 |
| 并发 | xdist 开进程不开线程，session fixture 每个 worker 各跑一次 |
| 重构的共同动机 | 该红没红、该说没说 —— 工程上最难查的不是红，是绿得没有理由 |

## 复习方法

1. **第一轮**：看着稿子念一遍，标记"念着别扭"的句子 → 换成自己的词
2. **第二轮**：闭卷讲，卡住就翻回来看，别硬撑
3. **第三轮**：只看六个问题，开口讲，讲完对稿子
4. 每轮不超过 20 分钟，**三轮之后基本就长在身上了**

⚠️ 别背书面语。面试官要听的是"你懂不懂"，不是"你背得好不好"。讲到某处突然口语化、举个自己的例子，反而是加分项。
